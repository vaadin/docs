= Annotation-Based Access Control

Access annotations on view classes define which users may navigate to a view. They're the most common way to control access to views. The following annotations are supported:

- [annotationname]`@AnonymousAllowed` permits anyone to navigate to a view without any authentication or authorization.
- [annotationname]`@PermitAll` allows any authenticated user to navigate to a view.
- [annotationname]`@RolesAllowed` grants access to users having the roles specified in the annotation value.
- [annotationname]`@DenyAll` disallows everyone from navigating to a view. This is the default: a view without an access annotation behaves as if it had [annotationname]`@DenyAll`.

The annotations are enforced by <<navigation-access-control#,navigation access control>>. In a Spring application, [classname]`VaadinSecurityConfigurer` enables it automatically, as described in <<../spring/setup#,Setting Up Spring Security>>. In other applications, enable it as described in <<../plain-servlet/setup#,Setting Up Security>>. Once it's enabled, none of the views are accessible until one of these annotations -- except [annotationname]`@DenyAll` -- is applied to them. For what users see when navigation is denied, see <<error-views#,Access-Denied & Not-Found Views>>.

The following example uses [annotationname]`@AnonymousAllowed` to let all users navigate to a view:

[source,java]
----
@Route(value = "", layout = MainLayout.class)
@PageTitle("Public View")
@AnonymousAllowed
public class PublicView extends VerticalLayout {
    // ...
}
----

[annotationname]`@PermitAll` lets any authenticated user navigate to a view, regardless of their roles:

[source,java]
----
@Route(value = "private", layout = MainLayout.class)
@PageTitle("Private View")
@PermitAll
public class PrivateView extends VerticalLayout {
    // ...
}
----

[annotationname]`@RolesAllowed` lets only users with one of the given roles navigate to a view:

[source,java]
----
@Route(value = "admin", layout = MainLayout.class)
@PageTitle("Admin View")
@RolesAllowed("ADMIN") // <- Should match one of the user's roles (case-sensitive)
public class AdminView extends VerticalLayout {
    // ...
}
----

How role names are matched depends on the application. With Spring Security, they're matched against the granted authorities, as described in <<../spring/roles-and-authorities#,Roles & Authorities>>. In other applications, they're passed unchanged to [methodname]`HttpServletRequest.isUserInRole()`.


== Parent Layouts

Access annotations on parent layouts are checked as well. This applies to automatic layouts -- classes annotated with [annotationname]`@Layout` -- to parent layouts set with the `layout` attribute of [annotationname]`@Route`, and to layouts defined with [annotationname]`@ParentLayout`. Both the layout and the view must grant access for navigation to succeed. A layout without an access annotation denies access to every view inside it, so a layout that hosts both public and protected views needs [annotationname]`@AnonymousAllowed`.


[[annotation-inheritance]]
== Annotation Inheritance

Access annotations are inherited from the closest parent class that has them. Annotating a child class overrides any inherited annotations. Interfaces aren't checked for annotations, only classes. In the following example, [classname]`UserListingView` requires the `ADMIN` role:

[source,java]
----
@RolesAllowed("ADMIN")
public abstract class AbstractAdminView extends VerticalLayout {
    // ...
}

@Route(value = "user-listing", layout = MainLayout.class)
@PageTitle("User Listing")
public class UserListingView extends AbstractAdminView {
    // ...
}
----



== Multiple Annotations on a Class

Use one access annotation per class. If a class has more than one, the following rules apply:

- [annotationname]`@DenyAll` overrides the other annotations
- [annotationname]`@AnonymousAllowed` overrides [annotationname]`@RolesAllowed` and [annotationname]`@PermitAll`
- [annotationname]`@RolesAllowed` overrides [annotationname]`@PermitAll`

= Setting Up Security

Vaadin's built-in view access control also works in applications that don't use Spring. This page describes how to set it up in a plain servlet application. For Spring Boot applications, see <<../spring#,Spring Applications>>.

Securing a plain servlet application takes the following:

- a way to authenticate users, and to set the user on the request;
- a log-in view, and a way to log out;
- a [interfacename]`VaadinServiceInitListener` that enables navigation access control, registered under `META-INF/services`; and
- an access annotation on each view class and on each layout class.


== Authenticating Users

Navigation access control reads the current user from [methodname]`HttpServletRequest.getUserPrincipal()`, and checks roles with [methodname]`HttpServletRequest.isUserInRole()`. The application can authenticate users against its own user store, such as a database, or let the servlet container do it. <<authentication#,Authenticating Users>> describes both approaches, and the [classname]`SecurityUtils` class that the examples on this page use.


[[log-in-view]]
== Log-in View

The log-in view is where navigation access control sends users who aren't authenticated when they try to open a protected view. The following example uses the <<{articles}/components/login#,Login>> component, but any view works:

.[filename]`LoginView.java`
[source,java]
----
@Route(value = "login", autoLayout = false)
@PageTitle("Login")
public class LoginView extends VerticalLayout {

    public LoginView() {
        LoginForm login = new LoginForm();
        login.addLoginListener(event -> {
            if (SecurityUtils.authenticate(event.getUsername(),
                    event.getPassword())) {
                UI.getCurrentOrThrow().getPage().setLocation("./"); // <1>
            } else {
                login.setError(true);
            }
        });
        add(login);
    }
}
----
<1> Reloads the page at the root of the application, so that the following requests carry the authenticated user.

The log-in view doesn't need an access annotation. Navigation access control always allows navigation to the configured log-in view.


== Logging Out

The following example shows a log-out button in the header of the main layout:

.[filename]`MainLayout.java`
[source,java]
----
@AnonymousAllowed // <1>
public class MainLayout extends AppLayout {

    public MainLayout() {
        H1 logo = new H1("Vaadin CRM");
        logo.addClassName("logo");
        HorizontalLayout header;
        if (SecurityUtils.isAuthenticated()) {
            Button logout = new Button("Logout", click ->
                    SecurityUtils.logout());
            header = new HorizontalLayout(logo, logout);
        } else {
            header = new HorizontalLayout(logo);
        }

        // Other page components omitted.

        addToNavbar(header);
    }
}
----
<1> The access annotations of a layout are checked in addition to those of the views inside it. This layout hosts both public and protected views, so it allows anonymous access.

== Enabling Navigation Access Control

A [interfacename]`VaadinServiceInitListener` enables [classname]`NavigationAccessControl` for all UIs:

.[filename]`NavigationAccessCheckerInitializer.java`
[source,java]
----
import com.vaadin.flow.server.ServiceInitEvent;
import com.vaadin.flow.server.VaadinServiceInitListener;
import com.vaadin.flow.server.auth.NavigationAccessControl;
import org.vaadin.example.views.login.LoginView;

public class NavigationAccessCheckerInitializer implements VaadinServiceInitListener {

    private NavigationAccessControl accessControl;

    public NavigationAccessCheckerInitializer() {
        accessControl = new NavigationAccessControl(); // <1>
        accessControl.setLoginView(LoginView.class); // <2>
    }

    @Override
    public void serviceInit(ServiceInitEvent serviceInitEvent) {
        serviceInitEvent.getSource().addUIInitListener(uiInitEvent -> {
            uiInitEvent.getUI().addBeforeEnterListener(accessControl); // <3>
        });
    }
}
----
<1> Creates the navigation access control. It's enabled by default.
<2> Sets the view to which users who aren't authenticated are redirected.
<3> Adds the access control as a [interfacename]`BeforeEnterListener` to every UI, so that it checks every navigation.

To customize the access checkers or the decision resolver, see <<../access-control/navigation-access-control#plain-servlet-applications,Navigation Access Control>>.

Vaadin loads the listener with the Java Service Provider Interface (SPI). Create a file named `com.vaadin.flow.server.VaadinServiceInitListener` in the `META-INF/services` directory of the application resources, and put the fully qualified name of the listener class into it, for example:

.[filename]`src/main/resources/META-INF/services/com.vaadin.flow.server.VaadinServiceInitListener`
[source]
----
org.vaadin.example.security.NavigationAccessCheckerInitializer
----

For more information, see <<{articles}/flow/advanced/service-init-listener#,VaadinServiceInitListener>>.


== Access Annotations

Annotate each view class and each layout class with an access annotation, as described in <<../access-control#,View Access Control>>. The log-in view is the only exception.

[annotationname]`@AnonymousAllowed` is part of Vaadin. [annotationname]`@PermitAll`, [annotationname]`@RolesAllowed`, and [annotationname]`@DenyAll` come from the Jakarta Annotations API, which Vaadin doesn't add to your project. Add it to the dependencies in your [filename]`pom.xml` file:

[source,xml,subs="+attributes"]
----
<dependency>
    <groupId>jakarta.annotation</groupId>
    <artifactId>jakarta.annotation-api</artifactId>
    <version>{jakarta-annotation-version}</version>
</dependency>
----

If your application server provides the Jakarta Annotations API, as Jakarta EE servers do, add the dependency with the `provided` scope instead.

With this setup, users who aren't authenticated are redirected to the log-in view when they try to navigate to a view that requires authentication. For what authenticated users see when they navigate to a view for which they have no permission, see <<../access-control/error-views#,Access-Denied & Not-Found Views>>.

= Calling JavaScript from the Server
:toclevels: 2

The Element API contains methods for executing JavaScript in the browser from the server side.

Declare the JavaScript in a Java interface and call it through [methodname]`Element.executeJs(Class)`. The build collects the declared JavaScript into the frontend bundle, and the client runs it from there. Nothing is compiled from a string in the browser, so the call works under a <<{articles}/flow/security/protections/content-security-policy#vaadin-strict-csp,strict content security policy>>. [methodname]`callJsFunction()` [since:com.vaadin:vaadin@V25.4]#works under such a policy as well#, since it calls a function that already exists on the element -- unless an argument is a [classname]`JsFunction` built with [methodname]`JsFunction.of()`.

The other methods described on this page -- [methodname]`executeJs(String, Object...)`, [methodname]`JsFunction.of()`, and [methodname]`addJsInitializer(String, Object...)` -- send the JavaScript to the browser as a string that's compiled there. Avoid them for anything a declaration can express. [methodname]`addJsInitializer(JsFunction)` [since:com.vaadin:vaadin@V25.4]#works under such a policy as well#, when the function it's given is <<#declaring-snippets,declared as a snippet>> rather than built with [methodname]`JsFunction.of()`.


[[declaring-javascript]]
[role="since:com.vaadin:vaadin@V25.4"]
== Declaring JavaScript in Java

An interface annotated with [annotationname]`@JsDefinition` declares JavaScript that the build collects into the bundle. It also extends one of two marker interfaces, which decides what its methods declare: [interfacename]`JsInvokers`, covered in this section, for JavaScript that runs when a method is called; or [interfacename]`JsSnippets` for JavaScript that's only passed on as a function (see <<#declaring-snippets,Declaring Snippets>>). An interface can't extend both.

Call the declared JavaScript of a [interfacename]`JsInvokers` interface through [methodname]`Element.executeJs(Class)`, which hands out an implementation of the interface; calling a method of it schedules the JavaScript that the method declares.

Each method of the interface is annotated with [annotationname]`@JsExpression`, whose value is the JavaScript expression to run. The arguments of the call are available inside the expression as `$0`, `$1`, and so on, and the element the implementation was obtained from is `this`.

The arguments must be a type supported by the communication mechanism. The supported types are `String`, `Boolean`, `Integer`, `Double`, `JsonNode`, `Element`, `Component`, and `JsFunction`.

Passing a [classname]`JsFunction` built with [methodname]`JsFunction.of()` is allowed, but it brings the browser-side compilation back, since the client builds such a function from its body string. Declare a method for the JavaScript instead, or pass a function <<#declaring-snippets,declared as a snippet>>.

The last parameter of a method can be declared variadic, such as `String...`, to accept a variable number of trailing arguments instead of a fixed one. The build turns it into a JavaScript rest parameter, so reference it the same way as any other parameter and spread it where the expression needs the individual values.

.Declaring and calling a variadic method
[example]
====
[source,java]
----
@JsDefinition
public interface ClassNamesJs extends JsInvokers {

    @JsExpression("this.classList.add(...$0)")
    void add(String... classNames);
}
----

[source,java]
----
public void highlight() {
    getElement().executeJs(ClassNamesJs.class)
            .add("selected", "highlighted");
}
----
====

.Declaring and calling JavaScript through a `@JsDefinition` interface
[example]
====
[source,java]
----
@JsDefinition
public interface GreeterJs extends JsInvokers {

    @JsExpression("window.alert($0)")
    void showGreeting(String greeting);
}
----

[source,java]
----
public void greet(String message) {
    getElement().executeJs(GreeterJs.class).showGreeting(message);
}
----
====

A method returns `void`, [classname]`PendingJavaScriptResult`, or [classname]`JavaScriptResult` with a type argument, to retrieve a return value the same way an expression does (see <<#return-values,Return Values>>). Declaring [classname]`JavaScriptResult` with a type argument hands the value to its handlers already converted to that type, with no type token needed at the call site.

.Declaring JavaScript that returns a value
[example]
====
[source,java]
----
@JsDefinition
public interface OverflowJs extends JsInvokers {

    @JsExpression("return this.scrollWidth > this.clientWidth")
    PendingJavaScriptResult isContentClipped();
}
----

[source,java]
----
public void updateTooltip() {
    getElement().executeJs(OverflowJs.class)
            .isContentClipped()
            .then(Boolean.class, this::setTooltipEnabled);
}
----
====

Nothing about the JavaScript is decided at the call site: the build generates one function per declared expression into the bundle, and the client runs that function after looking it up by an identifier of the JavaScript. The expression itself is never sent to the browser, and a production bundle carries the generated functions only -- the Java names stay on the server.

An optimized production build, which is the default, collects only the definitions it can reach from the entry points of the application, the same way it collects [annotationname]`@JsModule` -- apart from the ones Flow's own jar declares, which are always collected. A definition that's only used through reflection, or from code that no route or other entry point leads to, is left out of that bundle, and a call to it fails in the browser; name it with [annotationname]`@Uses` on a class that's reached to keep it (see <<{articles}/flow/production/production-build#,Production Build>>). Development mode collects every definition.

[NOTE]
The interface is checked when [methodname]`executeJs(Class)` hands out the implementation. It must extend [interfacename]`JsInvokers` and be annotated with [annotationname]`@JsDefinition`. Every method must be annotated with [annotationname]`@JsExpression` and return `void`, [classname]`PendingJavaScriptResult`, or [classname]`JavaScriptResult` with a type argument that's known from the interface (see <<#typed-results,Typed Results>>); a method that returns a snippet type is refused with the method named. A `default` or `static` method is refused, since it's implemented in Java rather than declaring JavaScript to run in the browser.

When the JavaScript isn't about a particular element, declare it the same way and run it through [methodname]`Page.executeJs(Class)`, which works with global browser APIs instead of with an element (see <</flow/advanced/browser-access#declaring-javascript-in-java,Accessing the Browser Page>>).

[[declaring-snippets]]
=== Declaring Snippets

An interface annotated with [annotationname]`@JsDefinition` that extends [interfacename]`JsSnippets` instead of [interfacename]`JsInvokers` declares _snippets_: JavaScript that isn't run when a method is called. Its methods return a snippet type -- [classname]`JsFunction`, [classname]`JsSnippet`, [classname]`DomEventFilter`, [classname]`DomEventData`, or an interface that extends [classname]`JsSnippet` -- instead of `void` or [classname]`PendingJavaScriptResult`. Calling such a method answers with that value, which is passed on to something that calls it later in the browser, such as <<#passing-a-declared-function,[methodname]`addJsInitializer(JsFunction)`>>. Like any other declaration, the build collects the snippet into the bundle, so nothing is compiled from a string in the browser.

A snippet isn't bound to an element, so get the implementation of its interface from [methodname]`JsSnippets.of(Class)` rather than from [methodname]`executeJs(Class)`. The implementation holds no state, so it can be kept in a constant and shared.

An interface extends exactly one of [interfacename]`JsInvokers` and [interfacename]`JsSnippets`. Passing a [interfacename]`JsSnippets` interface to [methodname]`executeJs(Class)`, or a [interfacename]`JsInvokers` interface to [methodname]`JsSnippets.of()`, is a compile error, since each method accepts only the matching marker type. A method whose return type doesn't match the kind the interface declares is refused with the method named.

The arguments of the Java call are captured and available in the expression as `$0`, `$1`, and so on. The expression is the body of the function, so it has to `return` a value if the caller expects one. The function takes no parameters of its own, unless the method is annotated with [annotationname]`@JsFunctionParameterNames`, which names the parameters that the caller passes to the function when it calls it.


[[return-values]]
== Return Values

Add a listener to the [classname]`PendingJavaScriptResult` instance that a call answers with to access the value from a `return` statement in the JavaScript. This works the same way for a declared expression, an <<#execute-js,[methodname]`executeJs()` expression>>, and a function called through <<#call-js-function,[methodname]`callJsFunction()`>>. A declared method has to declare [classname]`PendingJavaScriptResult`, or [classname]`JavaScriptResult` with a type argument (see <<#typed-results,Typed Results>>), as its return type to give access to the result.

.Checking for support of Constructable Stylesheets in the browser
[example]
====
[source,java]
----
@JsDefinition
public interface FeatureDetectionJs extends JsInvokers {

    @JsExpression("return 'adoptedStyleSheets' in document")
    PendingJavaScriptResult supportsConstructableStylesheets();
}
----

[source,java]
----
public void checkConstructableStylesheets() {
    getElement().executeJs(FeatureDetectionJs.class)
            .supportsConstructableStylesheets()
            .then(Boolean.class, supported -> {
                if (supported) {
                    System.out.println(
                            "Feature is supported");
                } else {
                    System.out.println(
                            "Feature isn't supported");
                }
            });
}
----
====

If the return value is a JavaScript `Promise`, the client only sends the return value to the server when the `Promise` is resolved.

[[typed-results]]
[role="since:com.vaadin:vaadin@V25.4"]
=== Typed Results

Declare [classname]`JavaScriptResult` with a type argument instead of [classname]`PendingJavaScriptResult` to get the value already converted to that type, with no type token needed at the call site:

.Declaring a method that returns a typed result
[example]
====
[source,java]
----
@JsDefinition
public interface DeepThoughtJs extends JsInvokers {

    @JsExpression("return 42")
    JavaScriptResult<Integer> getAnswer();
}
----

[source,java]
----
public void revealAnswer() {
    getElement().executeJs(DeepThoughtJs.class).getAnswer()
            .then(answer -> Notification.show(
                    "The answer is " + answer));
}
----
====

The value is converted with Jackson, so any type Jackson can deserialize works, including beans and generic types such as `List<Person>`. A value that can't be converted to the declared type goes to the error handler passed to [methodname]`then()`, and fails a future obtained from [methodname]`toCompletableFuture()`; without an error handler, it's logged as a warning.

The type argument has to be known from the interface. It can be a concrete type, such as `JavaScriptResult<Integer>`. It can also be a type variable that an interface the definition extends binds to a concrete type. A raw or wildcard [classname]`JavaScriptResult` is refused, and so is a type variable that no interface binds to a concrete type, since nothing says what to convert the value to.

With [classname]`JavaScriptResult<JsonNode>`, the handlers get the JSON as the browser sent it. To choose the Java type at the call site instead, by calling [methodname]`then()` with a [classname]`Class` or [classname]`TypeReference`, declare the method as returning [classname]`PendingJavaScriptResult` (see <<#deserializing-generic-types-with-typereference,Deserializing Generic Types with TypeReference>>).


[[deserializing-generic-types-with-typereference]]
=== Deserializing Generic Types with TypeReference

The [methodname]`then()` method accepts a [classname]`Class` parameter for simple types, but this doesn't work for generic types like `List<Person>` due to Java type erasure. For these cases, use the Jackson [classname]`TypeReference` overloads.

.Deserializing a JavaScript array into a `List<Person>`
[example]
====
[source,java]
----
@JsDefinition
public interface ItemsJs extends JsInvokers {

    @JsExpression("return this.getItems()")
    PendingJavaScriptResult getItems();

    @JsExpression("return this.getPersonMap()")
    PendingJavaScriptResult getPersonMap();
}
----

[source,java]
----
getElement().executeJs(ItemsJs.class).getItems()
        .then(new TypeReference<List<Person>>() {},
                items -> {
                    // items is List<Person>
                    items.forEach(person ->
                            System.out.println(person.getName()));
                });
----
====

An error handler can be provided as a second callback. It receives an error message as a `String` when the JavaScript execution fails [since:com.vaadin:vaadin@V25.4]#or the returned value can't be converted to the target type#:

[source,java]
----
getElement().executeJs(ItemsJs.class).getItems()
        .then(new TypeReference<List<Person>>() {},
                items -> processItems(items),
                errorMessage -> handleError(errorMessage));
----

[since:com.vaadin:vaadin@V25.4]#Without an error handler, a value that can't be converted is logged as a warning and the result handler isn't run.#

You can also use [methodname]`toCompletableFuture(TypeReference)` to get the result as a [classname]`CompletableFuture`:

[source,java]
----
CompletableFuture<Map<String, Person>> future = getElement()
        .executeJs(ItemsJs.class).getPersonMap()
        .toCompletableFuture(
                new TypeReference<Map<String, Person>>() {});
----

If the execution fails [since:com.vaadin:vaadin@V25.4]#or the returned value can't be converted to the target type#, the future completes exceptionally with a [classname]`JavaScriptException`. [since:com.vaadin:vaadin@V25.4]#When the value can't be converted, its cause is the conversion error.#


[[execute-js]]
== `executeJs` Method

The [methodname]`Element.executeJs()` method runs a JavaScript expression given as a string. The browser compiles the expression, so a strict content security policy blocks the call. Declare the JavaScript in Java instead (see <<#declaring-javascript,Declaring JavaScript in Java>>). Use this method only for JavaScript that can't be declared -- an expression that isn't known until runtime, for example.

The [methodname]`executeJs()` method accepts two parameters: the JavaScript expression to invoke; and the parameters to pass to the expression. The given parameters are available as variables named `$0`, `$1`, and so on.

The arguments passed to the expression must be a type supported by the communication mechanism. The supported types are `String`, `Integer`, `Double`, `Boolean`, `JsonNode`, `Element`, `Component`, and `JsFunction` (see <<#js-function,Passing JavaScript Functions>>).

.Calling `MyModule.complete(true)` on the client side
[example]
====
[source,java]
----
public void complete() {
    getElement().executeJs("MyModule.complete($0)", true);
}
----
====

.Passing a JSON array to a JavaScript expression
[example]
====
[source,java]
----
public void setItems(List<String> items) {
    getElement().executeJs("this.items = $0", items);
}
----
====

.Avoid Script Injection Vulnerabilities
[WARNING]
Always pass arguments using the `$0`, `$1`, ... notation to avoid script injection vulnerabilities. Never concatenate or interpolate strings to build JavaScript code to be executed.

If you need to run JavaScript without having access to an element, use the [methodname]`UI.getCurrentOrThrow().getPage().executeJs()` method.


[[call-js-function]]
== `callJsFunction` Method

The [methodname]`Element.callJsFunction()` method allows you to run a client-side component function from the server side. The method accepts two parameters: the name of the function to call; and the arguments to pass to the function.

The name of the function and the arguments [since:com.vaadin:vaadin@V25.4]#are sent to the browser, which looks the function up on the element and calls it. No JavaScript is compiled from a string for this call, so it works under a strict content security policy.# A dotted name, such as `$connector.method`, is resolved on the element property by property, and the function is called with the property it's read from as `this`.

The arguments passed to the function must be a type supported by the communication mechanism. The supported types are `String`, `Boolean`, `Integer`, `Double`, `JsonNode`, `Element`, `Component`, and `JsFunction` (see <<#js-function,Passing JavaScript Functions>>). Passing a [classname]`JsFunction` built with [methodname]`JsFunction.of()` brings the browser-side compilation back, since the client builds such a function from its body string. A function <<#declaring-snippets,declared as a snippet>> doesn't.

.Calling the `clearSelection()` JavaScript function on the root element from the server side
[example]
====
[source,java]
----
public void clearSelection() {
    getElement().callJsFunction("clearSelection");
}
----
====

.Calling the `expand(otherComponentElement)` JavaScript function on the root element from the server side
[example]
====
[source,java]
----
public void setExpanded(Component otherComponent) {
    getElement().callJsFunction("expand",
            otherComponent.getElement());
}
----
====

.Passing a JSON object to a JavaScript function
[example]
====
[source,java]
----
public void configure(String label, int count) {
    ObjectNode config = JacksonUtils.createObjectNode();
    config.put("label", label);
    config.put("count", count);
    config.put("enabled", true);
    getElement().callJsFunction("configure", config);
}
----
====


[[undelivered-invocations]]
[role="since:com.vaadin:vaadin@V25.3"]
== Undelivered Invocations

An invocation scheduled on the server is held in memory until it's written into a response for the browser. An application that keeps scheduling invocations which never reach the browser grows until it runs out of memory. Once 1000 invocations for one UI are waiting to be sent, Flow logs a warning naming the component they belong to, the expression of the most recent one, and why nothing is being delivered. The warning is logged once per UI.

Invocations pile up whenever nothing carries them to the browser:

- *The owner is detached.* An invocation for a detached element is held until that element is attached again, which never happens for a component the application has discarded.
- *The owner is invisible.* Invocations for an invisible component are kept until it becomes visible.
- *The UI has no open push connection.* Nothing is sent until the browser makes a request of its own, which a closed tab whose session hasn't expired yet never does.

Where only the latest value matters -- a progress value, a clock, a live measurement -- avoid scheduling a new invocation for every update:

- Keep the [classname]`PendingJavaScriptResult` that [methodname]`executeJs()` returns, and call [methodname]`cancelExecution()` on it before scheduling the next one.
- If the invocation only sets an element property, use [methodname]`Element.setProperty()` instead of [methodname]`executeJs()`. Only the last value of a property is sent.
- In a background task, compare [methodname]`UI.getLastUpdateSentTimestamp()` against the current time and stop scheduling updates while the browser isn't receiving them.

The timestamp is readable without the session lock, so a background task can decide whether to update the UI before acquiring it:

[source,java]
----
if (Duration.between(ui.getLastUpdateSentTimestamp(), Instant.now())
        .compareTo(STALE_THRESHOLD) < 0) {
    ui.access(() -> statusLabel.setText(statusText));
}
----

It tells when the pending updates were last written towards the browser, not that the browser received them, and for a UI that has had no response written yet it's the time the UI was created.

To find the code that schedules the invocations, enable debug logging for `com.vaadin.flow.component.internal.PendingJavaScriptInvocationUtil`, which then also logs the call site of the invocation that triggered the warning. Turning that logger off silences the warning.


[[js-function]]
[role="since:com.vaadin:vaadin@V25.2"]
== Passing JavaScript Functions

A [classname]`JsFunction` lets you build a reusable JavaScript function on the server and pass it as a parameter to [methodname]`executeJs()` or [methodname]`callJsFunction()`. The function arrives on the client as a real callable function with its captured values pre-bound, so you don't need to concatenate JavaScript fragments to embed server-side values.

The function body is compiled on the client, so a strict content security policy blocks it -- also when the function is passed to a method of a JavaScript definition. Where the body is known in advance, declare the JavaScript in Java instead (see <<#declaring-javascript,Declaring JavaScript in Java>>).

The first argument to [methodname]`JsFunction.of()` is a JavaScript function body. The remaining arguments are captured values, referenced inside the body as `$0`, `$1`, &hellip; using the same naming convention as [methodname]`executeJs()` parameters.

.Defining a function and invoking it
[example]
====
[source,java]
----
JsFunction greet = JsFunction.of(
        "return $0 + ' ' + $1;", "Hello", "World");
getElement().executeJs(
        "this.textContent = $0();", greet);
----
====

Captures may be any value supported as an [methodname]`executeJs()` parameter. An attached `Element` arrives as the corresponding DOM node; a detached `Element` arrives as `null`.

.Capturing an element
[example]
====
[source,java]
----
Div target = new Div();
add(target);

JsFunction mutate = JsFunction.of(
        "$0.textContent = 'updated';",
        target.getElement());
getElement().executeJs("$0();", mutate);
----
====


=== Declaring Runtime Arguments

Use [methodname]`withArguments()` to declare named parameters that the function accepts at call time. The body references them by name, and the JavaScript that invokes the function passes them positionally:

.A function with runtime arguments
[example]
====
[source,java]
----
JsFunction format = JsFunction
        .of("return prefix + ':' + suffix;")
        .withArguments("prefix", "suffix");
getElement().executeJs(
        "this.textContent = $0('alpha', 'beta');", format);
----
====


=== Controlling `this`

In JavaScript, the value of `this` inside a function depends on how the function is invoked, not where it is defined. The body of a [classname]`JsFunction` follows this convention &ndash; `this` is not bound to the host element automatically.

When the function is invoked as `$0(...)` from inside an [methodname]`executeJs()` expression, the body's `this` is the global object (or `undefined` in strict mode), not the element on which [methodname]`executeJs()` was called. To set `this` explicitly, invoke the function with [methodname]`Function.prototype.call()`: its first argument becomes `this` inside the body.

.Calling the function with a specific `this`
[example]
====
[source,java]
----
JsFunction setOwnText = JsFunction
        .of("this.textContent = msg;")
        .withArguments("msg");
getElement().executeJs(
        "$0.call(this, 'host element text');", setOwnText);
----
====

If the body always needs to reference the same element regardless of how the function is called, pass it as a capture instead of relying on `this`.


[[add-js-initializer]]
[role="since:com.vaadin:vaadin@V25.2"]
== Client-Side Lifecycle With `addJsInitializer`

The [methodname]`Element.addJsInitializer()` method registers a JavaScript initializer that runs each time a client-side DOM node is created for the element, and whose returned cleanup callback runs when that DOM node is discarded or the returned [classname]`Registration` is removed.

Use this when you need to install something on the client-side DOM &ndash; an event listener, a third-party widget, an observer &ndash; and reliably tear it down. A one-shot [methodname]`executeJs()` call doesn't cover two cases: a real re-attach gives the element a brand-new DOM node that no longer has your listener, and cleanup from a server-side detach listener cannot be delivered because the element is leaving the tree.

Pass the initializer as a `String` expression, or [since:com.vaadin:vaadin@V25.4]#as a [classname]`JsFunction` declared as a snippet#.

=== Passing an Expression

The [methodname]`addJsInitializer(String, Object...)` overload takes the initializer as a JavaScript expression. The expression is compiled in the browser, so a strict content security policy blocks it.

The expression syntax is the same as [methodname]`executeJs()`: `this` is the host element on the client, and parameters are referenced as `$0`, `$1`, &hellip;. If the expression returns a function, that function is invoked at teardown.

.Installing a listener with cleanup
[example]
====
[source,java]
----
Registration registration = getElement().addJsInitializer("""
        const handler = (event) => console.log($1, event.target);
        this.addEventListener($0, handler);
        return () => this.removeEventListener($0, handler);
        """, "click", "clicked");
----
====

Here `$0` is `"click"` and `$1` is `"clicked"`, so the event type and the log label come from the server rather than being hard-coded in the expression.

[[passing-a-declared-function]]
[role="since:com.vaadin:vaadin@V25.4"]
=== Passing a Declared Function

The [methodname]`addJsInitializer(JsFunction)` overload takes the initializer as a function instead of as an expression. Declare it as a snippet of a [annotationname]`@JsDefinition` interface that extends [interfacename]`JsSnippets` (see <<#declaring-snippets,Declaring Snippets>>) and obtain it through [methodname]`JsSnippets.of()`, so nothing is compiled from a string in the browser and the initializer works under a strict content security policy:

.Declaring an initializer and passing it to `addJsInitializer`
[example]
====
[source,java]
----
@JsDefinition
public interface ListenJs extends JsSnippets {

    @JsExpression("""
            const listener = () => this.classList.toggle($0);
            this.addEventListener('click', listener);
            return () => this.removeEventListener('click', listener);""")
    JsFunction toggleOnClick(String className);
}
----

[source,java]
----
getElement().addJsInitializer(
        JsSnippets.of(ListenJs.class).toggleOnClick("active"));
----
====

The function runs with the element as `this`, at the same moments as a `String` initializer. The arguments of the call that created the snippet are available as `$0`, `$1`, &hellip; in its expression.

The initializer is called with no arguments. A function that declares parameters of its own -- with [annotationname]`@JsFunctionParameterNames` or [methodname]`JsFunction.withArguments()` -- is rejected with an [classname]`IllegalArgumentException`. Pass the values the function needs as arguments of the snippet method instead.

Remove the registration on the server when the listener is no longer needed; the cleanup callback then runs on the client, for either overload.


=== Re-Attach Semantics

The initializer is re-run after a real re-attach &ndash; when the element is removed from the DOM in one round trip and re-added in a later one, and so the browser receives a fresh DOM node. It is *not* re-run when the element is detached and re-attached on the server inside a single round trip, because the client never discarded its DOM.


=== Cleanup Constraints

The return value of the initializer is read synchronously. A function is treated as the cleanup callback; returning `null`, `undefined`, or nothing at all (no `return`) means there's no cleanup. Returning any other value &ndash; including a `Promise` resolving to a function &ndash; is logged as an error on the client.

If setup is asynchronous, don't return the `Promise`. Keep a reference to the pending work and return a cleanup function that awaits it before tearing down. Awaiting the same promise in the cleanup callback ensures the resource is torn down even if cleanup runs before the asynchronous setup has finished &ndash; otherwise a slow import could create the widget after cleanup has already run, leaking it:

[source,java]
----
getElement().addJsInitializer("""
        const widgetPromise = import('./my-widget.js')
                .then((module) => module.create(this));
        return async () => (await widgetPromise).destroy();
        """);
----

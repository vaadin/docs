= Conversation History & Session Persistence

ifdef::flow[]

The orchestrator tracks conversation history internally. Use [methodname]`getHistory()` to get a snapshot and [methodname]`withHistory()` to restore it.


== Persisting History

Store the orchestrator in a field of the view. Use a [classname]`ResponseListener` to capture the history after each successful exchange and queue the snapshot for a background writer.

[source,java]
----
this.orchestrator = AiOrchestrator
        .builder(provider, systemPrompt)
        .withMessageList(messageList)
        .withInput(messageInput)
        .withResponseListener(event -> {
            if (event.getError().isPresent()) {
                return;
            }
            var history = this.orchestrator.getHistory();
            historyWriter().execute(() -> saveToDatabase(sessionId, history));
        })
        .build();
----

In this example, [methodname]`historyWriter()` returns an application-managed background executor that writes each conversation's snapshots in submission order. Implement [methodname]`saveToDatabase()` to store the snapshot.

The listener fires once per turn for both successful and failed exchanges -- check [methodname]`event.getError()` to tell them apart. It is not called when history is restored via [methodname]`withHistory()`, and empty responses (turns where the model emitted only tool calls or no visible content) are not appended to history. The event also carries the [since:com.vaadin:vaadin@V25.3]#finish reason and token usage# of the turn -- see <<listeners#response-metadata,Response Metadata>>.

.UI Updates from ResponseListener
[IMPORTANT]
While the UI is attached, the <<listeners#response-listener,response listener>> holds the session lock, so it can update UI components directly. Capture the snapshot in the listener and write it to storage on a background thread. If the UI detaches before the callback runs, the listener can still save the history.

The orchestrator restores its history, populates the Message List, and rebuilds the mappings for attachment clicks. A built-in LLM provider also replays the messages into its own memory.

If the application owns the chat memory, load the saved conversation into that memory as well. This applies to a [classname]`SpringAiLlmProvider` whose [classname]`ChatClient` uses a chat memory advisor or can't be inspected. It also applies to a [classname]`LangChain4jLlmProvider` whose <<llm-providers#langchain4j-customizer,customizer>> sets [methodname]`chatMemory()` or [methodname]`chatMemoryProvider()`.

[NOTE]
[methodname]`getHistory()` returns a point-in-time snapshot. If called while a streaming response is in progress, the snapshot may include the user message without its corresponding assistant response. Use [classname]`ResponseListener` to capture history at the right time.


== Data Model

Conversation history is represented as a list of [classname]`ChatMessage` records with four fields:

- [methodname]`role()` -- `USER` or `ASSISTANT`
- [methodname]`content()` -- the text content
- [methodname]`messageId()` -- UUID assigned to user messages; `null` for assistant messages. Used as the correlation key for attachments.
- [methodname]`time()` -- timestamp; may be `null`

File attachments are represented as [classname]`AiAttachment` records with [methodname]`name()`, [methodname]`mimeType()`, and [methodname]`data()` (raw bytes). Attachments are not stored in [classname]`ChatMessage` -- they are correlated separately via the message ID.


== Session Persistence

[classname]`AiOrchestrator` is serializable. Conversation history, UI component bindings, listener registrations, and display names are preserved across serialization. However, the LLM provider, tool objects, and the controller are transient -- they are not serialized and must be restored after deserialization.

=== Reconnecting after Deserialization

After the session is restored, call [methodname]`reconnect()` to supply a new provider and optionally restore tools and file attachments. Call [methodname]`apply()` to replay the saved conversation into provider-owned memory. If the application owns the memory, load the conversation into it before the next prompt. The message list, input, and file receiver retain their state across session restoration.

[source,java]
----
orchestrator.reconnect(provider)
        .withTools(tools)                   // optional
        .withController(controller)         // optional
        .withAttachments(savedAttachments)  // optional
        .apply();
----

Provider settings such as the streaming mode and <<llm-providers#background-execution,background execution>> live on the provider and are not serialized; apply them to the new provider instance before passing it to [methodname]`reconnect()`.

.Controller Reattachment
[NOTE]
[classname]`AiController` instances, including [classname]`GridAiController`, [classname]`ChartAiController`, and [classname]`FormAiController`, are not serialized with the orchestrator. Create a new controller after session restore and pass it to [methodname]`withController()` on the reconnector. The grid and chart controllers each have their own state capture and restoration API. The form controller has no separate state object, because the form fields themselves are persisted with the [classname]`VaadinSession`. See <<ai-powered-grid#,AI-Powered Grid>>, <<ai-powered-chart#,AI-Powered Chart>>, and <<ai-powered-form#,AI Form Filler>> for the specifics.

If [methodname]`prompt()` is called before reconnecting, it throws an [classname]`IllegalStateException`.

.LlmProvider Implementations
[NOTE]
[classname]`LlmProvider` implementations are not serializable. Always create a new provider instance after session restore and pass it to [methodname]`reconnect()`.

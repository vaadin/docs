= MCP Servers

A Model Context Protocol (MCP) server publishes tools over a standard protocol, so an assistant can call them without any tool-specific Java code in the application. The orchestrator itself is not an MCP client: MCP support lives in the AI framework that the <<llm-providers#,LLM provider>> wraps. Configure an MCP client there, and its tools reach the model through the same tool-calling pipeline as everything else -- the model invokes them exactly as it invokes a <<tool-calling#,tool object>> or a <<controllers#,controller>> tool.

Spring AI is the recommended framework for this, since its MCP client plugs straight into the [classname]`ChatClient` that [classname]`SpringAILLMProvider` accepts.


== How the Pieces Fit Together

Four layers are involved:

. The **MCP client** -- part of Spring AI -- connects to the MCP server, lists its tools, and exposes each one as a Spring AI tool callback.
. The **chat client** -- a Spring AI [classname]`ChatClient` -- carries those callbacks and executes them when the model asks for them.
. The **LLM provider** -- [classname]`SpringAILLMProvider` -- wraps the chat client for the orchestrator.
. The **orchestrator** -- [classname]`AIOrchestrator` -- runs the conversation and adds the application's own tools to each request.

The orchestrator appends the tools registered with [methodname]`withTools()` and [methodname]`withController()` to each request rather than replacing what the chat client already carries, so MCP tools and application tools coexist on the same orchestrator. The orchestrator builder has no MCP-specific methods: from its point of view, the model has more tools available than before.

.Preview Feature
[NOTE]
AI integration is a preview feature that requires the `com.vaadin.experimental.aiComponents` feature flag; see <<index#,AI Integration>>. MCP itself needs nothing extra to turn on, because it's framework configuration rather than a Vaadin feature.


== Adding the MCP Client

Add Spring AI's MCP client starter alongside the Spring AI model dependency the application already uses. The version comes from the Spring AI BOM:

[source,xml]
----
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-mcp-client</artifactId>
</dependency>
----

This starter supports all three standard transports -- a local stdio process, HTTP with Server-Sent Events (SSE), and streamable HTTP -- on top of the JDK HTTP client. Use `spring-ai-starter-mcp-client-webflux` instead for the WebFlux-based variants of the two HTTP transports.


== Transport Configuration

Each connection is a named entry under `spring.ai.mcp.client`. A local process over stdio is configured with the command to run:

[source,yaml]
----
spring:
  ai:
    mcp:
      client:
        stdio:
          connections:
            my-server:
              command: /usr/bin/python3
              args:
                - /opt/my-server/server.py
              env:
                MY_SERVER_TOKEN: ${MY_SERVER_TOKEN}
----

A remote server over streamable HTTP is configured with a base URL and the endpoint path:

[source,yaml]
----
spring:
  ai:
    mcp:
      client:
        streamable-http:
          connections:
            my-server:
              url: https://mcp.example.com
              endpoint: /mcp
----

The older SSE transport uses `sse-endpoint` for the path of the event stream:

[source,yaml]
----
spring:
  ai:
    mcp:
      client:
        sse:
          connections:
            my-server:
              url: https://mcp.example.com
              sse-endpoint: /sse
----

Several settings apply to every connection: `spring.ai.mcp.client.request-timeout` (20 seconds by default), `spring.ai.mcp.client.type` (`sync` or `async`, `sync` by default), and `spring.ai.mcp.client.name` and `.version`, which identify the application to the server during the MCP handshake. Turning tools into callbacks is on by default and can be disabled with `spring.ai.mcp.client.toolcallback.enabled=false`.

.Stdio Runs per Application, Not per User
[IMPORTANT]
A stdio connection starts one local child process per application instance, shared by every user session on that instance, and it has to run on the same host as the application. That's convenient during development and for a server bundled with the application, but a deployed application that serves many users is usually better off with the server exposed over streamable HTTP.


== Building the Provider

The starter contributes a [classname]`ToolCallbackProvider` bean holding the MCP tools. Register it as a default tool on the chat client, and wrap that client in a [classname]`SpringAILLMProvider`:

[source,java]
----
@Route("assistant")
public class AssistantView extends VerticalLayout {

    public AssistantView(ChatClient.Builder chatClientBuilder,
            ToolCallbackProvider mcpToolCallbacks) {
        var chatMemory = MessageWindowChatMemory.builder().build();
        var chatClient = chatClientBuilder
                .defaultTools(mcpToolCallbacks)
                .defaultAdvisors(advisors -> advisors
                        .advisors(MessageChatMemoryAdvisor
                                .builder(chatMemory).build())
                        .param(ChatMemory.CONVERSATION_ID,
                                UUID.randomUUID().toString()))
                .build();
        var provider = new SpringAILLMProvider(chatClient);

        var messageList = new MessageList();
        messageList.setMarkdown(true);
        var messageInput = new MessageInput();

        var orchestrator = AIOrchestrator
                .builder(provider, """
                        You are an in-app assistant. Use the available \
                        tools to answer questions about the user's data.
                        """)
                .withMessageList(messageList)
                .withInput(messageInput)
                .build();

        add(messageList, messageInput);
    }
}
----

The chat client is built per view here rather than as a singleton bean, because a provider -- and therefore the client behind it -- may belong to only one orchestrator. See the one-per-instance rule in <<index#,AI Integration>>.

.Memory Belongs to the Chat Client
[NOTE]
A provider created from a [classname]`ChatClient` does not manage conversation memory; the application owns it. That's why the example configures a chat memory advisor and a conversation id of its own: without them the model sees each prompt in isolation, however long the conversation looks in the Message List. A conversation id per client keeps two views from sharing one memory. See <<llm-providers#,LLM Providers>> for what the provider expects and what it logs when the client can't keep a conversation.

.Keep Guidance in the System Prompt
[TIP]
The orchestrator passes its system prompt on every turn, which replaces any [methodname]`defaultSystem()` text configured on the chat client. Put instructions about when to reach for the MCP tools in the system prompt given to [methodname]`AIOrchestrator.builder()`, not in the client's defaults.


== Combining MCP Tools With Application Tools

MCP tools do not exclude the application's own tools. An orchestrator can draw on an MCP server for the parts of the domain the server models, and on local Java tools for everything that has to run inside the application:

[source,java]
----
var orchestrator = AIOrchestrator
        .builder(provider, systemPrompt)
        .withMessageList(messageList)
        .withInput(messageInput)
        .withTools(new NavigationTools(ui))
        .withController(reportController)
        .build();
----

Tool names have to be unique across all of these. Spring AI prefixes MCP tool names with an identifier derived from the connection to keep servers from colliding with each other, but it doesn't know about the tools the orchestrator adds. Names must also match `^[a-zA-Z0-9_-]{1,64}$`, which is checked for controller tools at build time but not for names coming from an MCP server. Prefix the application's own tool names, and check that the server's names -- including the prefix Spring AI adds -- stay within the pattern and the length limit.


== Carrying the User's Identity

The connections configured under `spring.ai.mcp.client` are opened once per application instance, with one set of credentials taken from configuration. They authenticate the application, not the person using it. Two arrangements make the logged-in user's identity reach the server.

The first is to pass the identity with each call. Spring AI copies the entries of its tool context into the `_meta` field of every MCP request, so a value set on the session's chat client travels with each tool invocation:

[source,java]
----
var chatClient = chatClientBuilder
        .defaultTools(mcpToolCallbacks)
        .defaultToolContext(Map.of("userId", currentUserId()))
        .build();
----

This keeps a single pooled connection to the server and leaves it to the server to decide what that user may see and do. It only works if the server trusts the application to state who the user is, since the identity travels inside the protocol rather than as a credential on the transport.

The second is to open a connection per session and authenticate it as the user, bypassing the connection properties and building the client directly. In the following example, `tokens` is the application's own holder for the signed-in user's access token:

[source,java]
----
var transport = HttpClientStreamableHttpTransport
        .builder("https://mcp.example.com")
        .endpoint("/mcp")
        .httpRequestCustomizer(
                (request, method, uri, body, context) -> request.header(
                        "Authorization",
                        "Bearer " + tokens.currentAccessToken()))
        .build();
var mcpClient = McpClient.sync(transport).build();
mcpClient.initialize();

var chatClient = chatClientBuilder
        .defaultTools(SyncMcpToolCallbackProvider.builder()
                .mcpClients(mcpClient)
                .build())
        .build();
----

The server then applies its own authorization to both the tool list and every call, which is usually what per-user access control needs. The cost is one MCP session per user session: register a detach or session-destroy listener that closes the client, and expect the server to hold state for as long as the user is signed in.

The lambda passed to [methodname]`httpRequestCustomizer()` runs for every outgoing request, so it reads the token each time rather than baking one copy into the transport. An MCP session outlives a typical access token, and a token captured once at construction leaves every later tool call failing with an authorization error and nothing in the conversation to explain it.

.Capture the Identity Before the Turn Starts
[IMPORTANT]
With a streaming model or <<llm-providers#background-execution,background execution>>, tool calls run outside the request thread, where [methodname]`UI.getCurrent()`, [classname]`VaadinSession`, and Spring Security's [classname]`SecurityContext` are all absent. That rules out resolving the user from a thread local inside a tool call or inside [methodname]`httpRequestCustomizer()`. Resolve the identity while building the session's chat client, or in [methodname]`AIController.onRequest()`, and keep it somewhere a background thread can read it -- a field, or a holder that refreshes itself, like the token source above.


== Varying the Tool Set at Runtime

Which MCP tools reach the model doesn't have to be fixed at startup.

An [classname]`McpToolFilter` bean decides, for each connection and tool, whether that tool becomes a callback at all. It receives the connection info and the MCP tool definition, so it can filter on the server's name, the tool's name, or anything in its annotations:

[source,java]
----
@Bean
McpToolFilter mcpToolFilter() {
    return (connectionInfo, tool) -> !tool.name().startsWith("admin_");
}
----

For decisions that depend on the current user or the current view, filter later instead. The chat client asks each of its [classname]`ToolCallbackProvider` instances for callbacks once per prompt, so a provider of your own is consulted again on every turn and can return a different set each time:

[source,java]
----
ToolCallbackProvider allowedTools = () -> Arrays
        .stream(mcpToolCallbacks.getToolCallbacks())
        .filter(callback -> permissions
                .allows(callback.getToolDefinition().name()))
        .toArray(ToolCallback[]::new);

var chatClient = chatClientBuilder
        .defaultTools(allowedTools)
        .build();
----

Because the provider is re-consulted per prompt, `permissions` can follow the user as they navigate: update it on navigation, and the next prompt sees the tool set for the view the user is on.

The third option is to bypass Spring AI's tool plumbing and expose MCP tools through an <<controllers#custom-controller,[classname]`AIController`>>. Its [methodname]`getTools()` is also called before every request, and a [classname]`LLMProvider.ToolSpec` carries the name, description, and JSON Schema as plain values, which fits a tool set derived from a metadata model at runtime. This route works the same with either built-in provider and gives control over <<controllers#tool-error-handling,what the model learns when a call fails>>:

[source,java]
----
public class McpBridgeController implements AIController {

    private static final TypeReference<Map<String, Object>> ARGUMENTS =
            new TypeReference<>() {
            };

    private final McpSyncClient mcpClient;
    private final ObjectMapper json = new ObjectMapper();

    public McpBridgeController(McpSyncClient mcpClient) {
        this.mcpClient = mcpClient;
    }

    @Override
    public List<LLMProvider.ToolSpec> getTools() {
        return mcpClient.listTools().tools().stream()
                .filter(this::isAllowedForCurrentUser)
                .map(this::toToolSpec)
                .toList();
    }

    private LLMProvider.ToolSpec toToolSpec(McpSchema.Tool tool) {
        return new LLMProvider.ToolSpec() {
            @Override
            public String getName() {
                return tool.name();
            }

            @Override
            public String getDescription() {
                return tool.description();
            }

            @Override
            public String getParametersSchema() {
                return json.writeValueAsString(tool.inputSchema());
            }

            @Override
            public String execute(JsonNode arguments) {
                var request = McpSchema.CallToolRequest
                        .builder(tool.name())
                        .arguments(json.convertValue(arguments, ARGUMENTS))
                        .build();
                var result = mcpClient.callTool(request);
                if (Boolean.TRUE.equals(result.isError())) {
                    // Relayed to the LLM so it can correct the call.
                    throw new ToolException(textOf(result));
                }
                return textOf(result);
            }
        };
    }

    private static String textOf(McpSchema.CallToolResult result) {
        return result.content().stream()
                .filter(McpSchema.TextContent.class::isInstance)
                .map(content -> ((McpSchema.TextContent) content).text())
                .collect(Collectors.joining("\n"));
    }
}
----

[classname]`ToolSpec` expects a JSON Schema string, which is what an MCP tool's `inputSchema` already is, and it hands arguments over as a [classname]`JsonNode` from `tools.jackson.databind`. Keep the schema within the portable subset described in <<controllers#custom-controller,Building a Custom Controller>>; a server that emits keywords such as `$ref` or `format` may trip up some LLM providers.


== LangChain4j

[classname]`LangChain4JLLMProvider` is constructed from a [classname]`ChatModel` or [classname]`StreamingChatModel` and runs the tool-calling loop itself. LangChain4j's own MCP integration, [classname]`McpToolProvider`, attaches to an AI service built with [classname]`AiServices`, so there is no place to hand it to the provider.

With LangChain4j, MCP tools therefore reach the orchestrator one of two ways: through the Spring AI provider described above, or through the controller bridge in the previous section, which is framework-agnostic and works with either provider. The MCP client can be LangChain4j's [classname]`DefaultMcpClient` or the [classname]`McpSyncClient` from the MCP Java SDK; only the calls inside [methodname]`getTools()` and [methodname]`execute()` differ.


== Security Considerations

An MCP server is a source of instructions to the model, not only a set of functions, so treat what it returns with the same suspicion as any other external input.

.Treat Tool Descriptions as External Input
[IMPORTANT]
Tool names, descriptions, schemas, and results from an MCP server all end up in the model's context. A third-party server -- or a compromised one -- can use any of them to steer the assistant, including telling it to call other tools with data it has already seen. Point the orchestrator at servers you control or trust, and don't rely on the system prompt to contain a server that turns hostile.

.Tool Calls Run With the Application's Permissions
[IMPORTANT]
A tool call is an ordinary outbound request made by the application. Vaadin's view-level security governs which views a user can open; it does not inspect what a tool does once the model calls it. An MCP server reachable from the orchestrator is reachable for every user of that orchestrator unless the server itself, a tool filter, or a controller restricts it. Give each connection the narrowest credentials that still let it do its job, and enforce per-user authorization on the server whenever the connection carries the user's identity.

.Keep the Conversation Out of Logs You Don't Control
[TIP]
Tool arguments are written by the model from the conversation, so they can contain anything the user typed. Check what the MCP server logs before pointing the assistant at data you would not want in that log.

= LLM Providers

ifdef::flow[]

An AI framework -- such as Spring AI or LangChain4j -- is a Java library that handles the protocol details of talking to LLM services like OpenAI or Anthropic. The orchestrator plugs into your chosen framework through the [classname]`LlmProvider` interface. Create a provider by instantiating the appropriate implementation directly. Two implementations are provided: one for Spring AI and one for LangChain4j.

.Memory Window Limit
[IMPORTANT]
Both built-in providers maintain a 30-message memory window of their own. The exceptions are a [classname]`SpringAiLlmProvider` whose [classname]`ChatClient` has a chat memory advisor or can't be inspected, and a [classname]`LangChain4jLlmProvider` whose <<#langchain4j-customizer,customizer>> sets a chat memory. There, the application owns the memory. Older messages are evicted from the provider's working memory. The orchestrator's [methodname]`getHistory()` retains the full conversation, but the LLM only sees the most recent 30 messages.


== Spring AI

[classname]`SpringAiLlmProvider` supports both streaming and synchronous Spring AI models.

[source,java]
----
// From ChatModel - use an implementation of Spring AI ChatModel
ChatModel chatModel = OpenAiChatModel.builder()
    .openAiClient(...).options(...).build();
SpringAiLlmProvider provider = new SpringAiLlmProvider(chatModel);

// From ChatClient - use a Spring AI ChatClient
ChatClient chatClient = ChatClient.builder(...)
    .defaultAdvisors(...).build();
SpringAiLlmProvider provider = new SpringAiLlmProvider(chatClient);
----

The provider manages its own conversation memory using a 30-message window. A provider created from a [classname]`ChatClient` does so too, unless the client already has a chat memory advisor, such as Spring AI's [classname]`MessageChatMemoryAdvisor`. The application then owns the client's memory. The provider also leaves the memory to the application when a custom [classname]`ChatClient` implementation doesn't create its requests with a client built by [methodname]`ChatClient.builder()`, because it can't inspect that client's configuration.

Streaming is enabled by default. To disable it, call [methodname]`setStreaming(false)`:

[source,java]
----
provider.setStreaming(false);
----

In synchronous mode, the whole exchange runs in the request that triggered it and blocks the UI until the response is complete. See <<#background-execution,Background Execution>> for keeping the UI responsive during long prompts.

.History Restoration with an Application-Owned Memory
[NOTE]
A provider with its own memory restores the conversation into it, so [methodname]`withHistory()` and [methodname]`reconnect()` need no extra work. When the application owns the client's memory, the provider can't do that, and its [methodname]`setHistory()` does nothing. It logs a warning when the client's memory advisor has no default conversation id. Without one, the advisor has no conversation to read, and every prompt fails. Load the conversation into the client's own [classname]`ChatMemory` before passing the client to the provider, or leave the memory advisor out and let the provider handle it. The orchestrator's own conversation history and the Message List are restored either way.


== LangChain4j

[classname]`LangChain4jLlmProvider` supports both streaming and synchronous LangChain4j models. The mode is determined by the model type passed to the constructor:

[source,java]
----
// Streaming mode - use an implementation of LangChain4j StreamingChatModel
StreamingChatModel streamingChatModel = OpenAiStreamingChatModel.builder()
    .apiKey(...).modelName(...).build();
LangChain4jLlmProvider provider = new LangChain4jLlmProvider(streamingChatModel);

// Synchronous mode - use an implementation of LangChain4j ChatModel
ChatModel chatModel = OpenAiChatModel.builder()
    .apiKey(...).modelName(...).build();
LangChain4jLlmProvider provider = new LangChain4jLlmProvider(chatModel);
----

The provider manages its own conversation memory using a 30-message window, unless a <<#langchain4j-customizer,customizer>> replaces it.

Synchronous mode blocks the UI for the duration of each exchange; see <<#background-execution,Background Execution>>.


[[langchain4j-customizer]]
[role="since:com.vaadin:vaadin@V25.4"]
=== AI Service Customizer

The provider runs each turn through a LangChain4j AI service, which it builds with [classname]`AiServices`. Both constructors also accept a customizer as a second argument. The customizer receives the [classname]`AiServices` builder before the provider builds the service. Use it to add LangChain4j features with LangChain4j's own API, such as retrieval-augmented generation, MCP tool providers, tool objects, guardrails, and listeners:

[source,java]
----
LangChain4jLlmProvider provider = new LangChain4jLlmProvider(
        streamingChatModel,
        service -> service
                // Retrieval from the application's embedding store
                .contentRetriever(contentRetriever)
                .inputGuardrails(promptInjectionGuardrail));
----

Whatever the customizer configures, the provider keeps doing what the orchestrator needs from it:

* It supplies the tools of each turn next to the customizer's tools.
* It adds the <<session-context#,session context>> and the attachments to the user message.
* It reports the <<listeners#response-metadata,response metadata>>.
* It calls the model passed to the constructor, so a model set in the customizer isn't used.
* It sends the system prompt of the orchestrator in place of a [methodname]`systemMessage()` set in the customizer, unless that prompt is `null` or blank.

The provider sets the following on the builder before the customizer runs, so the customizer can replace each of them:

[cols="1,2"]
|===
|Builder method |Set by the provider

|[methodname]`chatMemory()`
|The provider's own conversation memory.

|[methodname]`hallucinatedToolNameStrategy()`
|A tool result that tells the model that the tool it called doesn't exist.
|===

The following applies to what the customizer configures:

* **Chat memory:** A memory set with [methodname]`chatMemory()` or [methodname]`chatMemoryProvider()` replaces the provider's own, and LangChain4j fills it as it does for any AI service. It also receives the tool calls and their results, including those of a turn that failed or was cancelled. With output guardrails, it keeps the answer as the model gave it, not as the guardrails returned it. The application owns that memory. The provider skips it during [methodname]`withHistory()` and [methodname]`reconnect()`, so load the saved conversation into it before the next prompt.
* **Retrieval and input guardrails:** Retrieval works on the text of the user message, which ends with the session context of the turn. Input guardrails check the message after retrieval, so they also see the retrieved content and the attachments. Both run before the model is called, on the thread that sends the prompt, also with a streaming model. Enable <<#background-execution,background execution>> so that they don't block the UI.
* **Output guardrails:** The response is the text that the output guardrails returned. LangChain4j runs them on the final answer only, so text that the model sends next to its tool calls isn't passed on. With a streaming model, the answer arrives in one piece once the guardrails have checked it. The provider's own chat memory keeps the answer as the guardrails returned it, so later turns continue from what the user received. When a guardrail fails the turn, the answer it rejected stays in the chat memory, unless the guardrail asks LangChain4j to remove it with [methodname]`fatalWithMessageRemoval()` or [methodname]`failureWithMessageRemoval()`.
* **Moderation:** A moderation model set in the customizer isn't used, because LangChain4j applies it only to service methods annotated with [annotationname]`@Moderate`. Use an input guardrail to check the user message instead.
* **Tool names:** Give the tools you add in the customizer names that no [methodname]`withTools()` tool or controller uses. LangChain4j rejects two tools of the same name, and every turn that has both then fails.
* **Tool errors:** LangChain4j handles the errors of tools added in the customizer, with the tool error handlers set there or with its defaults. Unless the customizer sets both [methodname]`toolArgumentsErrorHandler()` and [methodname]`toolExecutionErrorHandler()`, LangChain4j logs a notice that asks for them, once, also when the customizer adds no tools. The notice doesn't concern the tools of the orchestrator, whose errors never reach these handlers. Setting both handlers chooses how the tools you add fail, and LangChain4j then logs no notice.


[[framework-features]]
== Framework Features

An LLM provider is a thin adapter: it hands each prompt to the framework and streams back what the framework produces. Everything else the model needs is set up in the framework, with the framework's own API. The orchestrator works with whatever has been configured there and adds no framework features of its own.

Where the setup goes depends on the framework. With Spring AI, configure a [classname]`ChatClient` and wrap it in a provider. With LangChain4j, set the model's own options on the model, and configure the AI service in a <<#langchain4j-customizer,customizer>>.

Model Context Protocol (MCP) servers are the most common example. Neither the orchestrator nor the provider is an MCP client. Configure the framework's MCP client: its transport, its credentials, and which of the server's tools the model may see. Then hand its tools to the provider. With Spring AI, register the tool callbacks on a [classname]`ChatClient`:

[source,java]
----
ChatClient chatClient = ChatClient.builder(chatModel)
        // Tool callbacks from Spring AI's MCP client
        .defaultTools(mcpToolCallbacks)
        .build();
SpringAiLlmProvider provider = new SpringAiLlmProvider(chatClient);
----

With LangChain4j, add a [classname]`McpToolProvider` in the customizer:

[source,java]
----
// Tool provider for LangChain4j's MCP client
McpToolProvider mcpToolProvider = McpToolProvider.builder()
        .mcpClients(mcpClient)
        .build();
LangChain4jLlmProvider provider = new LangChain4jLlmProvider(chatModel,
        service -> service.toolProvider(mcpToolProvider));
----

The MCP tools then reach the model on every turn, next to any tools registered on the orchestrator through <<tool-calling#,[methodname]`withTools()`>> or a <<controllers#,controller>>. The model calls all of them the same way, so tool names have to be unique across every source and match `^[a-zA-Z0-9_-]{1,64}$` -- validated when a controller is registered, but not for names that come from an MCP server.

Other framework features work the same way: configure them in the framework, then create the provider. This covers the following:

* Retrieval-augmented generation against a vector store
* Guardrails, including content moderation
* Observability
* Model options such as temperature and token limits
* Structured output with schema validation
* Limits on the tool-calling loop of a turn

The framework's own reference documentation is where to look for the details:

* https://docs.spring.io/spring-ai/reference/[Spring AI reference documentation]
* https://docs.langchain4j.dev/[LangChain4j documentation]

.System Prompt Precedence
[TIP]
Pass a system prompt to [methodname]`AiOrchestrator.builder()` to override the framework default on every turn. If the prompt is `null` or blank, the provider uses any [methodname]`defaultSystem()` text on the Spring AI client or [methodname]`systemMessage()` set in the LangChain4j customizer.

== Background Execution

A synchronous provider produces the response on the thread that asks for it. For a prompt sent from the browser, that is the request thread: the request does not return until the model has produced the complete response, including any tool calls along the way. The interface freezes for the whole wait, and since the request holds the session lock, other views in the same session wait too.

Background execution moves the exchange to a background thread instead. Enable it on either built-in provider:

[source,java]
----
provider.setBackgroundExecution(true);
----

The user's message then appears immediately and the Message List shows a <<{articles}/components/message-list#typing-indicator,typing indicator>> while the model works, the UI stays responsive, and the response replaces the indicator when the model finishes. The setting is off by default. It's read for each prompt, so it can be changed at any time; the next prompt uses the new mode.

With a streaming model, the response already arrives on the LLM client's own threads, so the setting has no effect on a [classname]`SpringAiLlmProvider` in streaming mode. A [classname]`LangChain4jLlmProvider` with a streaming model still starts each turn on the thread that sends the prompt. The retrieval and the input guardrails of a <<#langchain4j-customizer,customizer>> run there, before the model is called. Background execution moves that start to a background thread as well.

The response is now produced outside any request, so it reaches the browser through server push or polling. Enable push by annotating the application shell with [annotationname]`@Push` (see <<index#server-push,Server Push>>), or enable polling with [methodname]`UI.setPollInterval()`. Without either, the response only shows up with the next request the browser happens to make -- the page looks stuck even though the turn completed on the server. The provider logs a warning, once per provider instance, when neither is active; the same warning applies in streaming mode, whose response also arrives outside a request. Manual push mode is not enough on its own, because nothing in the framework calls `ui.push()` for the application.

Everything that the orchestrator does before it hands the prompt to the provider still runs in the request thread:

* The <<request-interception#,request interceptor>>
* Adding the user's message to the Message List and showing the typing indicator
* [methodname]`AiController.onRequest()`
* The request listener
* The session context supplier

The model calls, every tool execution, and the [classname]`ResponseListener` run on a background thread, as do the retrieval and the input guardrails of a LangChain4j customizer. There, [methodname]`UI.getCurrent()` and other Vaadin thread locals return `null` and components must not be touched directly. Thread-bound framework state, such as Spring Security's [classname]`SecurityContext`, is absent there for the same reason.

Wrap component access in `ui.access()`, or capture what a tool needs in [methodname]`AiController.onRequest()` while the request thread is still current -- see <<tool-calling#,Tool Calling & Programmatic Prompts>> and <<controllers#,Controllers>>. The built-in controllers already handle this. [methodname]`AiController.onResponse()` is the exception: the orchestrator calls it through `ui.access()`, so it can update components directly.

.One Prompt at a Time
[NOTE]
The orchestrator processes one prompt at a time. In the default synchronous mode, a message submitted while a turn is running waits for the session lock and is processed when the turn ends. With a streaming provider or with background execution, the turn outlives the request that started it and the lock is free. The orchestrator then <<component-interfaces#disabling-submit,disables submitting>> on the input until the turn ends. A [methodname]`prompt()` call made during the turn is ignored with a server-side warning.

If the user closes or reloads the browser tab while a turn is running, the turn still completes on the server: the response is recorded in the conversation history and the [classname]`ResponseListener` fires as usual. Only the UI updates are skipped, along with [methodname]`AiController.onResponse()`, which needs an attached UI. The setting itself lives on the provider and is not serialized with the session -- apply it again to the recreated provider after a session restore, before passing it to [methodname]`reconnect()`. See <<conversation-history#,Conversation History & Session Persistence>>.


[[custom-llm-providers]]
== Custom LLM Providers

Implement the [classname]`LlmProvider` interface to connect to any LLM framework:

[source,java]
----
public class MyLlmProvider implements LlmProvider {

    @Override
    public Flux<String> stream(LlmRequest request) {
        // Return a reactive stream of response tokens
        // request.userMessage()    -- the user's prompt
        // request.attachments()    -- any file attachments
        // request.systemPrompt()   -- the system prompt
        // request.tools()          -- tool objects registered via withTools()
        // request.explicitTools()  -- ToolSpec tools contributed by the controller
        // request.sessionContext() -- per-turn session context, or null
        // request.metadataSink()   -- consumer for response metadata
    }

    @Override
    public void setHistory(List<ChatMessage> history,
            Map<String, List<AiAttachment>> attachmentsByMessageId) {
        // Restore conversation context
    }
}
----

A provider is responsible for its own conversation memory, for the tool-calling loop over both the vendor-annotated tool objects and the framework-agnostic [classname]`ToolSpec` tools (see <<controllers#,Controllers>>), and for appending the <<session-context#,session context>> to the user message when one is given.

The response stream carries text only. The provider can also [since:com.vaadin:vaadin@V25.3]#publish the finish reason and token usage# of the turn through the [methodname]`metadataSink()` consumer on the request. Each call carries everything observed so far and replaces the value of any earlier call, so publish whenever the provider learns more -- a turn that fails midway has then still reported what was observed. Pass `null` for any value the framework doesn't report; a provider that observes no metadata never calls the consumer. See <<listeners#response-metadata,Response Metadata>> for how applications read it.

The orchestrator calls [methodname]`stream()` on the thread that triggers the prompt and subscribes to the returned stream on that same thread -- whether a turn runs in the background is decided entirely by the implementation. An implementation whose LLM call blocks should schedule that call itself; otherwise it occupies the request thread and holds the session lock for the whole turn. See <<#background-execution,Background Execution>> for how the built-in providers expose this as a setting.

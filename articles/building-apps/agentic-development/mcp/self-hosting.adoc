= Self-Hosting the MCP Server

Vaadin runs a hosted MCP server at https://mcp.vaadin.com/docs[mcp.vaadin.com/docs], and for most teams that's the one to use: there's nothing to operate, and the documentation corpus behind it is refreshed weekly.

Self-hosting is for the teams that can't point a development tool at a service outside their own perimeter. The same server ships as a container image you run yourself, on your own host, inside your own network. This page covers getting it licensed, running, and connected.

== What Self-Hosting Changes

Three properties of the image are the reason to run it yourself:

*It needs no network at runtime.* The documentation corpus, the search indexes, and the embedding model are all baked into the image at build time. Every tool answers from the image's own filesystem, so the container runs with no egress at all -- no route, no DNS, no phone home. Vaadin verifies that on every release by running the image in a sealed network namespace and calling every tool through it.

*Every tool call can be recorded.* Point the server at a path and it appends one JSON record per tool call, so you have a log of what your agents asked for. See <<#audit-logging,Audit Logging>>.

*Nothing is reported to Vaadin.* Analytics reporting is off unless you supply an Amplitude API key, which a self-hosted deployment has no reason to do. If an image that merely *contains* the reporting code is unacceptable to your security review, it can be left out of the binary altogether -- see <<#custom-image,Requesting a Custom Image>>.

What you give up is corpus freshness. The hosted server picks up new documentation weekly without you doing anything; a self-hosted one is as current as the image you last pulled.


[[hosted-server]]
== What the Hosted Server Runs

The image you pull is the image Vaadin runs. There's no internal build for `mcp.vaadin.com` and a separate public one for customers: the bytes that pass the release smoke test are the bytes both pull, so the hosted server and yours answer from the same code and the same documentation corpus.

What differs is the configuration, and it comes to three things:

* *Analytics are on.* The hosted server reports tool calls to Amplitude, which is how Vaadin sees which tools earn their place. Yours reports nothing unless you set a key -- see <<#analytics,Analytics>>.
* *Audit logging is off.* Vaadin keeps no per-call record of what anyone asked the hosted server. Needing one is a reason to self-host -- see <<#audit-logging,Audit Logging>>.
* *It runs in the EU.* Queries to `mcp.vaadin.com` are served from EU-hosted infrastructure.

So if what rules out the hosted server for you is where the queries go rather than what the server does, those three lines are the whole of the difference.


== What You Need

* *A container runtime on an x86_64 host.* Docker, Podman, or any Kubernetes cluster. The published image is `linux/amd64` only, so an arm64 host -- Apple Silicon, or Graviton and its equivalents -- runs it under emulation, at a cost in both start-up time and search latency. Fine for trying it out; not what to deploy on.
* *A Vaadin license key entitled to the MCP server.* The container refuses to start without one. See <<#getting-a-license-key,Getting a License Key>>.
* *About 1 vCPU and 2 GB of memory per instance.* See <<#sizing,Sizing>> for measured figures.
* *A place to put it that your development tools can reach.* The server has no authentication of its own -- see <<#network-exposure,Network Exposure>>.


[[getting-a-license-key]]
== Getting a License Key

The server validates an *offline key*: the signed token you download from https://vaadin.com/myaccount/licenses[your Vaadin account]. A `proKey` is the credential for the online license check and isn't a license source for this server on any platform.

Two things have to be true of the key:

*It has to be a server license key, with no machine binding.* A machine-bound key names a machine ID that has to match the machine it runs on, and inside a container that ID is a property of the image rather than of your host -- it's derived from the home directory the base image wrote, so it's identical across every run and across separately built images of the same base. A key issued against a developer laptop never validates in the container, and one issued against the container is hostage to the base image. Ask for a server key.

*It has to be entitled to the MCP server product.* An ordinary Vaadin Pro subscription key is a valid key that doesn't cover this product, and it's refused with a message saying so. If your key is refused that way, contact Vaadin to have the entitlement added rather than looking for a configuration problem.

[NOTE]
.There Is No Unlicensed Mode
====
No property, profile, or environment variable starts the server without a license. Earlier builds had a bypass intended for local container runs; it was removed, because anything configurable by environment variable is reachable by anyone who can start the container. A container with no key exits with status `78` and a message naming the key.
====


== Running the Server

=== 1. Pull the Image

Images are published to `vaadin/mcp-server` on Docker Hub. Every build carries an immutable tag:

----
vaadin/mcp-server:<version>-<YYYYMMDD-HHMMSS>-<sha7>
----

For example, `vaadin/mcp-server:1.0.0-20260916-114956-2b7c708`.

`<version>` is the server's own version, the timestamp is when the build started, and `<sha7>` is the commit the image reports as its `build_commit`. `:latest` moves to the newest build once it passes its smoke test.

Pin the immutable tag in anything you deploy. The version number tracks the *code*, so a documentation refresh republishes under the same version with a new timestamp -- which means `:latest` and a bare version number both name a moving target, and the immutable tag is the only one that identifies exactly what you're running.

[source,bash]
----
docker pull vaadin/mcp-server:latest
----

=== 2. Install the License Key

There are two routes, and which one to use depends on how your platform delivers secrets.

*Route 1 -- environment variable.* Works on every hosting platform. The value is the token itself, not a path to it:

[source,bash]
----
docker run --rm -p 8080:8080 \
    -e VAADIN_OFFLINE_KEY="$(cat /path/to/serverKey)" \
    vaadin/mcp-server:latest
----

The value lands in `docker inspect` and in the process environment, so use an `--env-file` locally and your platform's secret store in a deployment. Under Docker Compose that's an `env_file:` or an `environment:` entry fed from the host -- a Compose `secrets:` entry arrives as a *file*, which this route can't read.

*Route 2 -- mount the key file.* This is the route for Docker and Compose secrets, and for Kubernetes secret volumes. The container runs as uid 65532, whose home directory is `/home/nonroot`, so the directory the license checker searches is `/home/nonroot/.vaadin`:

[source,bash]
----
docker run --rm -p 8080:8080 \
    -v "$HOME/.vaadin/serverKey:/home/nonroot/.vaadin/serverKey:ro" \
    vaadin/mcp-server:latest
----

Four things about that mount:

* *Keep the filename the download gave you.* The license checker reads a fixed list of names -- `offlineKeyV2`, `offlineKeyV2.txt`, `offlineKey`, `offlineKey.txt`, `serverKey`, `serverKey.txt` -- and it cross-checks the name against the content, so a renamed key is rejected as malformed. A key under `/root/.vaadin` isn't read at all.
* *The file has to be readable by uid 65532.* A root-owned `0600` key on a Linux host reads back as *no license file found*, which looks exactly like having mounted nothing. Copy the key somewhere you mount for nothing else and `chown 65532:65532` it; on Kubernetes, use a secret with `defaultMode: 0400` and a matching `runAsUser: 65532`. Docker Desktop remaps bind-mount ownership, so a Mac never sees this and a Linux host does.
* *Mount the one file, not your whole `~/.vaadin` directory.* Keys are tried in the order above and validation stops at the first one accepted, so a stray or foreign key that sorts ahead of your real one is what gets used.
* *`:ro` is enough.* Nothing is written back.

=== 3. Confirm It Started

The server prints one line to stderr at startup -- `ready. License valid until <date>.` -- and the same posture is on the health endpoint, which is `/health` rather than `/actuator/health`:

[source,bash]
----
curl -s http://localhost:8080/health | jq '.components.license.details.license'
----

[source,json]
----
{ "status": "valid", "expiresAt": "2027-04-30T00:00:00Z" }
----

If it didn't start, <<#license-refusals,License Refusals>> below matches each message to its cause.

Opening `http://localhost:8080/` in a browser gives you a landing page carrying the configuration snippets for this deployment, with your own endpoint URL already substituted in. It's rendered at startup rather than served as a static file, so the URL it advertises is the one this instance actually answers on.


== Pointing Your Tools at It

The MCP endpoint is `/docs`, relative to wherever the application is mounted. So a default deployment on `mcp.example.com` is configured as:

----
https://mcp.example.com/docs
----

Everything in the <<{articles}/building-apps/agentic-development/mcp/supported-tools/#,MCP Setup Guide>> applies unchanged -- substitute your own URL for `https://mcp.vaadin.com/docs` in any of the per-tool configuration snippets. The transport is streamable HTTP either way.

[[network-exposure]]
=== Network Exposure

*The server has no authentication.* There's no security layer on the classpath, and the health endpoint and the MCP endpoint are both unauthenticated by design -- it serves public Vaadin documentation, and the reason to self-host it is usually that you don't want the *queries* leaving your network, not that the answers are secret.

That makes network placement your control point. Put it behind your existing ingress, restrict it to the networks your developers and CI run on, and don't publish it to the internet.

=== Behind a Reverse Proxy

Three settings cover the deployment shapes:

`SERVER_SERVLET_CONTEXT_PATH`:: Mounts the whole application under a prefix. This is all a prefixed deployment needs: the server reads its own mount, so the landing page and the endpoint move together.

`VAADIN_MCP_ENDPOINT_PATH`:: Moves the endpoint within the mount. It defaults to `/docs` and can't be `/` -- the landing page routes the application root, so an endpoint there would reject every request. Use a context path for a prefix and leave the endpoint a path of its own.

`VAADIN_MCP_PUBLIC_ENDPOINT_URL`:: The absolute URL the landing page tells clients to configure. Set it for the one case the server can't see from inside: an ingress that *rewrites*, stripping a prefix before the request arrives. A deployment that only sets a context path needs nothing here.


== Configuration Reference

[cols="1,3"]
|===
|Variable |What It Does

|`VAADIN_OFFLINE_KEY`
|The offline key, as its token value. Also read from the `vaadin.offlineKey` system property and from key files under the home directory, in that order. Required, unless a key file is mounted.

|`SERVER_PORT`
|Port to listen on. Defaults to `8080`.

|`SERVER_SERVLET_CONTEXT_PATH`
|Mounts the application under a prefix. Empty by default.

|`VAADIN_MCP_ENDPOINT_PATH`
|Path the MCP transport answers on, relative to the mount. Defaults to `/docs`. May not be `/`.

|`VAADIN_MCP_PUBLIC_ENDPOINT_URL`
|Absolute URL advertised on the landing page. Derived from the mount and endpoint path when unset.

|`VAADIN_AUDIT_LOG_PATH`
|File to append audit records to. Unset means no audit log. See <<#audit-logging,Audit Logging>>.

|`AMPLITUDE_API_KEY`
|Enables analytics reporting to Amplitude. Leave unset -- see <<#analytics,Analytics>>.

|`VAADIN_MCP_DATA_PATH`
|Directory the documentation indexes are read from. Set correctly in the image; override only if you mount your own index tree.
|===


[[audit-logging]]
== Audit Logging

Name a file and the server appends one JSON Lines record per tool call:

----
VAADIN_AUDIT_LOG_PATH=/var/log/vaadin-mcp/audit.jsonl
----

Each line carries `ts`, `licenseKid`, `tool`, `args`, `durationMs`, and `status`. *Arguments, never results* -- the record says what was asked, not what came back. The shape is treated as a contract with your log shipper and has its own serializer, so application-wide JSON configuration can't move it.

Mount the directory somewhere the records survive a redeploy, and make it writable by uid 65532. Retention is yours: the server appends and never rotates, so point logrotate, journald, or your shipper at the file.

Startup prints which of the two states it's in, naming the path it opened, so a variable that didn't arrive is visible in the log rather than at your first audit. *A path that can't be opened refuses startup* -- deliberately, because an operator who asked for an audit trail and silently didn't get one is worse off than one who never asked.


[[analytics]]
== Analytics

Reporting to Amplitude is controlled by one environment variable, `AMPLITUDE_API_KEY`, and leaving it unset -- the default everywhere -- means the server performs no outbound analytics traffic whatsoever. A self-hosted deployment needs to do nothing. The hosted server at `mcp.vaadin.com` does set one -- see <<#hosted-server,What the Hosted Server Runs>>.

The published image does contain the reporting code, inert. If your security review requires that it be absent rather than merely disabled, it can be left out of the binary at build time: see <<#custom-image,Requesting a Custom Image>>.

Startup prints exactly one line about analytics, which is how a working deployment is told from a half-configured one: either *analytics enabled* with the endpoint it reports to, or *compiled in but no key at runtime*. An image with the branch compiled out prints neither.


[[sizing]]
== Sizing

Measured on a container constrained to one vCPU and 2 GB, serving the full documentation corpus for every bundled Vaadin version:

[cols="2,1"]
|===
|Measurement |Value

|Image size
|About 230 MB

|Cold start to first successful health check
|5 seconds

|Resident memory, model and all indexes open
|291 MB

|Search latency, p50 / p95, two concurrent clients
|8 ms / 42 ms

|Throughput, two concurrent clients
|178 req/s
|===

Treat these as a shape rather than a promise. They come from a natively built arm64 image on Apple Silicon rather than from the amd64 image you deploy, and a 1-vCPU slice on a laptop isn't a 1-vCPU slice on a server, so measure on your own hardware before sizing against them. One small instance comfortably serves a development team. Nothing in the server holds per-client state -- every request is self-contained -- so if you do need more headroom, run more replicas behind whatever load balancing you already have.


== Keeping the Documentation Current

The corpus is part of the image, so refreshing it means pulling a newer image and restarting. Vaadin rebuilds the newest release against the current documentation weekly and republishes it under the same version with a new timestamp tag, so there's a fresh image to pull roughly every week even when the server code hasn't changed.

To find out what an instance is actually serving, read the `vaadin-mcp://image-info` resource over MCP. It reports the build commit, the build date, the corpus each version was indexed from with its reference and commit, the license posture, and which optional artifacts the image carries. That's also the thing to quote in a support request -- it identifies the build exactly, where a tag can be ambiguous and a version number is deliberately coarse.

Upgrades are otherwise unremarkable: the image holds no state, so stopping the old container and starting the new one is the whole procedure. Read the release notes before a version change rather than a refresh, since a version bump is what signals that something a client negotiates against -- a tool, a parameter, a response field -- has moved.


[[license-refusals]]
== License Refusals

Every refusal exits with status `78` and prints a line naming the cause:

[cols="2,3"]
|===
|Message |Cause

|*no license file found*
|No key was found at all: the variable is unset, or the mount is at the wrong path, unreadable by uid 65532, or empty.

|*the offline key does not provide access to <product>*
|A real, valid key with no entitlement for this product. Contact Vaadin rather than changing configuration.

|*invalid offline key*
|The signature or the machine ID was rejected. The URL in the message carries the *container's* machine ID, not your host's -- which is why a machine-bound key can't work here.

|*an offline key could not be read*
|A key the library can't parse, as against one it refuses: a corrupt file, or a foreign one picked up from a mounted key directory. The message names the resolution order, because the key to replace is the first unusable one in that order and not necessarily the one you meant to use.

|*license expired*
|Past expiry and past the grace period.
|===

One state isn't a refusal: past expiry but inside the 30-day grace period, the server starts and serves normally, logging that it's in the grace period and by when it needs a renewed key. The health endpoint and the `vaadin-mcp://image-info` resource both carry the same posture, refreshed on a schedule rather than frozen at boot, so a monitor can catch an expiry the startup log announced weeks earlier.


[[custom-image]]
== Requesting a Custom Image

The published image suits almost every deployment, and it's the one Vaadin gates on a full smoke test of the running container before publishing. The server's source isn't public, so a variant is something to request rather than something to build -- but two variants exist, and both are decided when the image is built rather than by configuration afterward:

* *A thinner version set.* The published image indexes every Vaadin version the hosted server covers. Narrowing that to the versions your organization actually runs makes a smaller image.
* *Analytics compiled out.* Leaving `AMPLITUDE_API_KEY` unset means the reporting code is present and inert, which satisfies most security reviews. For the ones it doesn't, the code can be left out of the binary altogether -- but only at build time.

Raise either through your Vaadin support channel.

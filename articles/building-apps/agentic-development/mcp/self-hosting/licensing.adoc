= Licensing

The self-hosted server validates its license at startup and needs a key to serve. The key is supplied at run time rather than baked into the image, since an image carrying one would distribute it.


== Getting a Key

The server validates an *offline key*: the signed token you download from https://vaadin.com/myaccount/licenses[your Vaadin account]. A `proKey` is the credential for the online license check and isn't a license source for this server on any platform.

Two things have to be true of the key:

*It has to be a server license key, with no machine binding.* A machine-bound key names a machine ID that has to match the machine it runs on, and inside a container that ID is a property of the image rather than of your host -- it's derived from the home directory the base image wrote, so it's identical across every run and across separately built images of the same base. A key issued against a developer laptop never validates in the container, and one issued against the container is hostage to the base image. Ask for a server key.

*It has to be entitled to the MCP server product.* An ordinary Vaadin Pro subscription key is a valid key that doesn't cover this product, and it's refused with a message saying so. If your key is refused that way, contact Vaadin to have the entitlement added rather than looking for a configuration problem.

*One key covers every instance.* The key carries no machine binding, and the server counts nothing -- no seats, no instances, no concurrent callers. The same key serves a shared deployment and twenty developer machines alike, and nothing has to be issued per deployment.


== Installing the Key

Which route to use depends on how your platform delivers secrets.

=== Route 1: Environment Variable

Works on every hosting platform. The value is the token itself, not a path to it:

[source,bash]
----
docker run --rm -p 8080:8080 \
    -e VAADIN_OFFLINE_KEY="$(cat /path/to/serverKey)" \
    vaadin/mcp-server:latest
----

The value lands in `docker inspect` and in the process environment, so use an `--env-file` locally and your platform's secret store in a deployment. Under Docker Compose that's an `env_file:` or an `environment:` entry fed from the host -- a Compose `secrets:` entry arrives as a *file*, which this route can't read.

=== Route 2: Mounted Key File

This is the route for Docker and Compose secrets, and for Kubernetes secret volumes. The container runs as user ID 65532, whose home directory is `/home/nonroot`, so the directory the license checker searches is `/home/nonroot/.vaadin`:

[source,bash]
----
docker run --rm -p 8080:8080 \
    -v "$HOME/.vaadin/serverKey:/home/nonroot/.vaadin/serverKey:ro" \
    vaadin/mcp-server:latest
----

Four things about that mount:

* *Keep the filename the download gave you.* The license checker reads a fixed list of names -- `offlineKeyV2`, `offlineKeyV2.txt`, `offlineKey`, `offlineKey.txt`, `serverKey`, `serverKey.txt` -- and it cross-checks the name against the content, so a renamed key is rejected as malformed. A key under `/root/.vaadin` isn't read at all.
* *The file has to be readable by user ID 65532.* A root-owned `0600` key on a Linux host reads back as *no license file found*, which looks exactly like having mounted nothing. Copy the key somewhere you mount for nothing else and `chown 65532:65532` it; on Kubernetes, use a secret with `defaultMode: 0400` and a matching `runAsUser: 65532`. Docker Desktop remaps bind-mount ownership, so a Mac never sees this and a Linux host does.
* *Mount the one file, not your whole `~/.vaadin` directory.* Keys are tried in the order above and validation stops at the first one accepted, so a stray or foreign key that sorts ahead of your real one is what gets used.
* *`:ro` is enough.* Nothing is written back.


[[renewal]]
== Renewal and Expiry Warnings

*Renewal is a file copy.* Put the newer key in place by whichever route you installed the first one, then restart the container, which always takes effect. The server also re-probes its own license hourly, so a replaced key *file* is generally picked up without a restart; a key supplied as an environment variable is fixed for the life of the process and needs one.

*The warning arrives 30 days ahead, on four channels.* Inside that window the license is still valid and the server serves normally. Four channels carry it so that nobody has to be watching one particular place:

* *Startup*, on standard error, once per container start.
* *`/health`*, re-probed hourly -- the channel to alert on. See <<monitoring-and-audit-logging#,Monitoring and Audit Logging>>.
* *The MCP handshake*, so every client that connects reads the status in the server's `initialize` instructions.
* *Tool responses*, which is the channel worth knowing about in advance: during the warning window and the grace period, each tool result carries an appended `[PLEASE RELAY TO THE USER]` notice, so developers see the reminder in their agent's own output. Outside those windows nothing is appended.

After expiry the server keeps serving for a 30-day grace period, logging that it's in the grace period and the date it stops. Past that it stops serving.


[[license-refusals]]
== License Refusals

Every refusal exits with status `78` and prints a line naming the cause:

[cols="2,3"]
|===
|Message |Cause

|*no license file found*
|No key was found at all: the variable is unset, or the mount is at the wrong path, unreadable by user ID 65532, or empty.

|*the offline key does not provide access to <product>*
|A real, valid key with no entitlement for this product. Contact Vaadin rather than changing configuration.

|*invalid offline key*
|The signature or the machine ID was rejected. The URL in the message carries the *container's* machine ID, not your host's -- which is why a machine-bound key can't work here.

|*an offline key could not be read*
|A key the library can't parse, as against one it refuses: a corrupt file, or a foreign one picked up from a mounted key directory. The message names the resolution order, because the key to replace is the first unusable one in that order and not necessarily the one you meant to use.

|*license expired*
|Past expiry and past the grace period.
|===

One state isn't a refusal: inside the grace period the server starts and serves normally. See <<#renewal,Renewal and Expiry Warnings>> for that window and the channels that announce it.

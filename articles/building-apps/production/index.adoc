= Take Your Application to Production

These guides take your application from your development machine to production. They assume a Spring Boot application built with Maven, such as a project from https://start.vaadin.com[`start.vaadin.com`]. Each guide covers the essentials and the pitfalls that are specific to Vaadin, and links to the <<{articles}/flow/production#,Deploying to Production>> reference for the details.

Before you start, read <<{articles}/building-apps/architecture/runtime-model#,How Vaadin Works at Runtime>>. An application with Flow views keeps the UI state of each user in server memory. This affects most of the decisions in these guides: how much memory to give the JVM, how to configure the proxy, which URLs to use for health checks, and what happens to users when an instance stops.


== Reading Order

Read the guides in this order. Each one builds on the previous ones.

. <<build#,Build for Production>> creates a JAR that runs in production mode, and explains when the build needs Node.js and a license key.
. <<configure#,Configure the Application>> keeps production settings in a Spring profile, and secrets out of the source code.
. <<container#,Build a Container Image>> packages the JAR in an image, and gives the JVM enough memory for the sessions.
. <<reverse-proxy#,Deploy Behind a Proxy>> terminates TLS in a reverse proxy, and lets server push through it.
. <<health-checks#,Add Health Checks>> gives the load balancer and the container platform URLs to check, without creating sessions.
. <<logs-and-metrics#,Collect Logs & Metrics>> makes logs machine-readable, and exposes metrics on a port that users can't reach.
. <<ci#,Build on CI>> builds, tests, and packages the application on every change.


== Running More Than One Instance

These guides deploy a single instance. To run several instances behind a load balancer, you need sticky sessions, so that all requests of a user reach the instance that holds their session. When an instance stops, its users lose their UI state, unless the sessions are replicated to other instances. <<{articles}/building-apps/architecture/capacity-and-failover#,Measure Capacity and Test Failover>> shows how to measure what an instance can hold, and how to choose between accepting the reload, draining instances, and replicating sessions. For the architecture, see <<{articles}/flow/production/distributed-deployment#,Distributed Deployment Architecture>>.

To deploy to a servlet container instead of running an executable JAR, to a specific cloud provider, or as a GraalVM native image, see the <<{articles}/flow/production#,Deploying to Production>> reference.

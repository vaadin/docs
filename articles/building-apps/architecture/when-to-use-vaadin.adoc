= When to Use Vaadin

Most web frameworks are built for the public internet, where anyone can visit. Vaadin is built for the applications behind the login: the data-rich tools, back-office systems, and portals that an organization runs on, and that its employees, customers, and partners use for work. For those, its server-side approach saves a lot of work. For public websites, it costs more than it saves.

This page is for experienced Java developers who are evaluating Vaadin. It gives the top reasons to choose Vaadin, what they cost, and the top reasons to choose something else. The recommendations are Vaadin's opinion. <<runtime-model#,How a Vaadin Application Works>> explains the mechanics behind them.

Most of this page is about Flow views, which you write in Java and which run on the server. They're the default way to build a Vaadin application, and both the main benefits and the main costs come from them. A Vaadin application can also have React views, which run in the browser. Where React views change the picture, this page says so.

None of this means that Vaadin is only for large or long-lived systems. A small tool for a handful of users fits as well. A team with frontend skills can use those skills too, in React views and in UI components of its own.


== Top Reasons to Choose Vaadin

*Data-rich business applications for known users.* Vaadin includes the <<{articles}/components#,UI components>> that business applications are made of, such as grids, form fields, date pickers, dialogs, and layouts. Vaadin designs them for WCAG 2.1 level AA, and Flow views and React views use the same ones. A grid fetches only the rows that the user scrolls to, straight from an application service, and leaves filtering and sorting to the database. A form validates its input in Java. See <<{articles}/building-apps/forms-data/add-grid/paginated-data#,Add a Paginated Grid>> and <<{articles}/building-apps/forms-data/add-form/validation#,Form Validation>>. Because the users log in, their number has a known upper limit, and you can size the servers for it.

*Less to build and maintain.* Much of the work in a web application goes into parts that Vaadin either includes or makes unnecessary:

* A frontend stack that you assemble from separate libraries and keep up to date.
* A UI component library of your own.
* An API whose only client is your own user interface, which you design, version, document, and secure. A click listener in a Flow view calls your application services directly, in the same thread, as ordinary Java code.
* The coordination between a frontend team and a backend team. A Java developer can build a complete Flow view with Vaadin's UI components, layouts, and default theme, without writing HTML, CSS, or JavaScript.

*Security from server-side state.* The browser displays the UI components and sends user events to the server. The decisions -- what the user may see, what's valid, what happens next -- are made in Java, where the user can't change them. With security enabled, Flow views are denied until an annotation grants access, and Flow ignores events from UI components that are hidden or disabled. The services behind the views still need protection of their own, as described in <<{articles}/building-apps/security/protect-services#,Protect Services>>.

*Maintainable for years.* Because views are Java, the compiler and your IDE's refactoring tools cover the UI code too. When you change an entity or a service, you find the views that it affects at compile time, not in production. Vaadin releases on a published schedule, and a minor version deprecates features without removing them, so upgrading to it is usually a version bump. <<licensing-and-maintenance#,Licensing, Support & Maintenance>> describes the release and maintenance model.

*Fewer places for AI agents to go wrong.* An AI coding agent working on a Vaadin application has one language and one compiler from the UI to the data access, and no API contract between a frontend and a backend to keep in sync. The compiler rejects many of its mistakes before anything runs. <<{articles}/building-apps/testing#,Browserless tests>> run as plain JUnit tests, without a browser, so the agent can run them after every change. See <<{articles}/building-apps/agentic-development#,Agentic Development>>.

*Java teams own every layer.* Who builds the application matters as much as what it is. A team of Java developers can build and maintain the whole application without first learning a JavaScript framework and its toolchain.

*Modernizing Swing and older Vaadin applications.* A Flow view is a tree of UI components with listeners, written in Java -- much like a Swing user interface. The team's skills carry over, and so can the domain logic and services behind the old user interface. Applications built with older Vaadin versions already use the server-side model, although the API has changed since. <<{articles}/upgrading/version-comparison#,Vaadin Version Comparison>> shows how much. Vaadin also has <<{articles}/tools#,tools>> for modernizing older applications.


== What It Costs

The costs come from running the UI on the server, so they apply to Flow views. <<runtime-model#,How a Vaadin Application Works>> explains each of them in detail.

*Server memory per user and per tab.* The server keeps the UI of every open browser tab in memory, for as long as the tab stays open. How many users a server can handle depends on its memory, and on what your views hold. See <<#how-far-it-scales,How Far It Scales>>.

*A round trip per interaction that runs Java code.* A click with a server-side listener, navigating between views, and loading more rows into a grid all wait for the network. Over a local network, this is hard to notice. Over a slow mobile or intercontinental connection, every such interaction pays the delay. See <<runtime-model#which-interactions-need-the-server,Which Interactions Need the Server>>.

*A dependency on the connection.* A Flow view can't run any Java code while the connection is down, and it can't work offline. See <<runtime-model#when-the-connection-is-lost,When the Connection Is Lost>>.

*Stateful deployment.* Load balancers need sticky sessions, so that each user's requests reach the server that holds their UI. When a server stops -- because it crashed, the cluster scaled down, or you deployed a new version -- its users lose anything they hadn't saved, unless you replicate the sessions. See <<runtime-model#what-this-means-for-deployment,What This Means for Deployment>>.

*Less direct control over the rendered HTML.* You build a Flow view from UI components in Java, not from markup. You can <<{articles}/styling#,style>> the UI components, use <<{articles}/components/html-elements#,HTML elements>> from Java, and <<{articles}/building-apps/components#,wrap>> web components and React components of your own, but you don't write the markup of a view by hand.

React views avoid the first three costs: they keep their state in the browser, and contact the server only when they call a service. In exchange, they bring back some of what Flow views save you: a TypeScript frontend, the skills to build it, and services that the browser can call. Vaadin generates type-safe TypeScript clients for those services, so you don't design a REST API, but each service is now reachable from the browser, and becomes your security boundary. <<runtime-model#how-react-views-differ,How React Views Differ>> compares the two kinds of views.


== How Far It Scales

A Vaadin application scales out by adding servers behind a load balancer, like other Java web applications. The difference is that you have to plan for its state: the memory that each user costs, sticky sessions, and <<capacity-and-failover#test-what-users-see-when-a-server-stops,what happens to the sessions on a server that stops>>.

Memory decides the capacity of each server. According to https://vaadin.com/scalability[Vaadin Scalability], the session state of a concurrent user ranges from 50 to 1000 KB, depending on how much business data the session holds. In the example in <<capacity-and-failover#measure-memory-per-session,Measure Memory per Session>>, a session with one tab, showing a form and a lazily loaded grid, took about 290 KB. When the grid held all of its items in memory, each tab took about four times as much. Your own views decide the real figure. To keep it small, keep large data sets out of the session, for example with a <<{articles}/building-apps/forms-data/add-grid/paginated-data#,paginated grid>>.


== Top Reasons to Choose Something Else

If one of the following is among your top requirements, Vaadin recommends another tool, at least for that part of the application. These aren't all-or-nothing decisions: an application can use Vaadin for the parts behind the login, and something else for the rest.

*Large volumes of anonymous traffic.* A Flow view keeps a UI in server memory for every visitor, and an open tab keeps it alive, so memory grows with the number of concurrent visitors. React views keep no UI state on the server, so they suit a public part of a business application, such as a landing page or a sign-up form. A high-traffic public site, especially one with sudden spikes, is better built and scaled separately from the business application.

*Ranking in search engines.* Vaadin builds both kinds of views in the browser with JavaScript. It doesn't render pages to HTML on the server for search engines, and a Flow view keeps a UI on the server for every visitor, crawlers included. React views don't change this. Keep content pages on a content management system or a static site, and link from them to the Vaadin application.

*Mobile-first or offline-first applications.* Vaadin's layouts adapt to the screen size in the browser, but every interaction that runs Java code pays the latency of the mobile network, and a Flow view stops working when the connection drops. React views can keep working offline, but storing data in the browser and synchronizing it with the server is your own code. See <<{articles}/hilla/guides/client-caching#,Client-Side Data Caching>>. If most of the application has to work offline, most of it would be React views, and the benefits of writing the UI in Java no longer apply.

*A highly custom user interface.* Vaadin suits applications whose many views follow one consistent design. The default theme gives them a clean look without any CSS, and you can <<{articles}/styling#,style>> the UI components to match your brand. When a designer specifies each screen in detail, and the user interface is the product, a hand-written frontend gives you more control. React views give you that control within a view, and can still use Vaadin's UI components.

*Instant response to every keystroke or pointer movement.* A view such as a drawing canvas or a real-time editor can't wait for a round trip per interaction. Implement such views as React views. See <<runtime-model#choosing-flow-or-react-views,Choosing Flow or React Views>>.

*A separate frontend, or a public API anyway.* If the organization wants a separate frontend team with a framework of its own, or needs a public API for mobile applications and partners anyway, the benefits of one team and no API mostly don't apply. React views give you a React frontend with type-safe calls to Java services, but they're part of the Vaadin application, and are built and deployed with it. Their services serve the application's own views. A public API for other clients is something you design separately.


== Try It Before You Decide

The costs on this page depend on your views, your users, and your network, so Vaadin recommends that you measure them rather than rely on general figures:

. Build one view that's typical of your application, with realistic data, in the <<{articles}/getting-started/quick-start#,Quick Start>> project or a project of your own. The <<{articles}/getting-started/tutorial#,Tutorial>> shows how to build a complete one.
. Try the view at the latency your users have, as described in <<capacity-and-failover#measure-interaction-latency,Measure Interaction Latency>>.
. Measure how much memory a session with that view costs, and estimate from it how much memory your expected number of concurrent users and tabs needs, as described in <<capacity-and-failover#measure-memory-per-session,Measure Memory per Session>>.

Then read <<runtime-model#,How a Vaadin Application Works>> before you decide how to deploy, and <<licensing-and-maintenance#,Licensing, Support & Maintenance>> to see which features you'd use are free.

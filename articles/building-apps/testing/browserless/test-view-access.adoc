= Test View Access Control

This page covers Spring Security and Quarkus Security in separate sections.
For Java EE/CDI, use <<setup-cdi#,the CDI setup>> with your application's CDI access-control beans and login flow.

First configure <<{articles}/building-apps/security/protect-views#,view protection>> in your application.
These examples assume a public default route, a login view, and views restricted to specific roles.
Adapt the route names and roles to your application.

[#spring]
== Spring Security

Start with <<{articles}/building-apps/testing/browserless/setup-spring-boot#,the Spring Boot test setup>>.


[#spring-secured-context]
=== Simulate Users with a Secured Context

With [annotationname]`@SpringBootTest`, view access control works without extra setup.
Define the shared browserless application context with [methodname]`createSecured()` instead of [methodname]`create()`:

.`BrowserlessContextConfiguration.java`
[source,java]
----
import org.springframework.context.ApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.core.Authentication;
import com.vaadin.browserless.SecuredBrowserlessApplicationContext;
import com.vaadin.browserless.SpringBrowserlessApplicationContext;

@Configuration
public class BrowserlessContextConfiguration {

    @Bean
    SecuredBrowserlessApplicationContext<Authentication> browserlessApplicationContext(
            ApplicationContext applicationContext) {
        return SpringBrowserlessApplicationContext.createSecured(
                applicationContext, Application.class);
    }
}
----

A secured context is also a [classname]`BrowserlessApplicationContext`, so tests that don't need credentials can keep autowiring that type; their [methodname]`newUser()` creates an anonymous user.
Give each user the credentials to simulate when you create it:

* [methodname]`newUser()` creates an anonymous user, like Spring Security's [annotationname]`@WithAnonymousUser`.
* [methodname]`newUser("admin", "ADMIN")` creates an authenticated user with the given username and roles, like [annotationname]`@WithMockUser`. A role without the `ROLE_` prefix gets it.
* [methodname]`newUser(authentication)` installs any [classname]`Authentication` object, for example one built from your own user details.

The credentials are in place before the user's window opens and navigates to the root route, so a logged-in user isn't redirected to the login view, and custom redirect logic for authenticated users works as expected.
Each test creates its user with try-with-resources, so that the user is closed when the test ends:

.Tests with Simulated Users
[source,java]
----
import org.junit.jupiter.api.Assertions;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.security.core.Authentication;
import com.vaadin.browserless.SecuredBrowserlessApplicationContext;
import com.vaadin.flow.component.avatar.Avatar;
import com.vaadin.flow.component.html.Anchor;

@SpringBootTest
class ViewSecurityTest {

    @Autowired
    private SecuredBrowserlessApplicationContext<Authentication> app;

    @Test
    void anonymousUser_protectedView_redirectToLogin() {
        try (var anonymous = app.newUser()) {
            anonymous.newWindow().navigate("protected", LoginView.class);
        }
    }

    @Test
    void anonymousUser_publicView_signInLinkPresent() {
        try (var anonymous = app.newUser()) {
            var window = anonymous.newWindow();

            // public view is default page
            Assertions.assertInstanceOf(PublicView.class,
                    window.getCurrentView());

            Anchor anchor = window.find(Anchor.class).withText("Sign in")
                    .single();
            Assertions.assertTrue(
                    window.test(anchor).isUsable(),
                    "Sign in link should be available for anonymous user");
        }
    }

    @Test
    void adminUser_adminView_viewShown() {
        try (var admin = app.newUser("admin", "ADMIN")) {
            var window = admin.newWindow();

            window.navigate(AdminRoleView.class);

            Assertions.assertTrue(
                    window.find(Avatar.class).single().isVisible(),
                    "Avatar should be visible for logged users");
        }
    }
}
----

Closing the user also clears its authentication from the test thread, so that it doesn't leak into the next test.
Spring Security test annotations, such as [annotationname]`@WithMockUser`, don't affect the users of a secured context.


=== Test with a Reduced Application Context

In a test that selects its beans with [annotationname]`@SpringJUnitConfig` or [annotationname]`@ContextConfiguration` instead of loading the full application context, register view access control yourself.
Such a test doesn't component-scan the shared bean, so it also creates a secured application context of its own for each test, as described in <<setup-spring-boot#context-per-test,Create an Application Context for Each Test>>.
Vaadin applies access control through a [classname]`NavigationAccessControl` registered as a [classname]`BeforeEnterListener` for the UI.
Provide a [classname]`VaadinServiceInitListener` that registers it, in a test configuration class:

.Set Up NavigationAccessControl in a Test Configuration
[source,java]
----
import org.springframework.boot.test.context.TestConfiguration;
import org.springframework.context.annotation.Bean;
import com.vaadin.flow.server.VaadinServiceInitListener;
import com.vaadin.flow.spring.security.SpringNavigationAccessControl;

@TestConfiguration
class TestViewSecurityConfig {

    @Bean
    VaadinServiceInitListener setupViewSecurityScenario() {
        SpringNavigationAccessControl accessControl = new SpringNavigationAccessControl();
        accessControl.setLoginView(LoginView.class);
        return event -> {
            event.getSource().addUIInitListener(uiEvent -> {
                uiEvent.getUI().addBeforeEnterListener(accessControl);
            });
        };
    }
}
----

Annotate the class with [annotationname]`@TestConfiguration` rather than [annotationname]`@Configuration`.
Spring Boot's component scan skips test configuration classes, so the class doesn't leak into `@SpringBootTest` contexts in the same package, which already have access control.

Alternatively, import the out-of-the-box [classname]`NavigationAccessControlInitializer`, which requires only a [classname]`NavigationAccessControl` bean:

.Set Up NavigationAccessControl with NavigationAccessControlInitializer
[source,java]
----
import org.springframework.boot.test.context.TestConfiguration;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Import;
import com.vaadin.flow.server.auth.NavigationAccessControl;
import com.vaadin.flow.spring.security.NavigationAccessControlInitializer;
import com.vaadin.flow.spring.security.SpringNavigationAccessControl;

@TestConfiguration
@Import({NavigationAccessControlInitializer.class})
class TestViewSecurityConfig {

    @Bean
    NavigationAccessControl navigationAccessControl() {
        SpringNavigationAccessControl accessControl = new SpringNavigationAccessControl();
        accessControl.setLoginView(LoginView.class);
        return accessControl;
    }
}
----

Use this variant only in a reduced context.
With Spring Security, a `@SpringBootTest` context already defines a `navigationAccessControl` bean, so importing the class there fails with a bean definition override error.

When the test needs custom user objects or complex grant rules, load the user from a [classname]`UserDetailsService` and pass an [classname]`Authentication` for it to [methodname]`newUser()`.
The following test provides its own [classname]`UserDetailsService`, and also includes the [classname]`TestViewSecurityConfig` class from the start of this section, which applies view access control:

.Tests with a Mock UserDetailsService
[source,java]
----
import java.util.List;
import java.util.UUID;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.Assertions;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.TestConfiguration;
import org.springframework.context.ApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.test.context.junit.jupiter.SpringJUnitConfig;
import com.vaadin.browserless.BrowserlessUIContext;
import com.vaadin.browserless.SecuredBrowserlessApplicationContext;
import com.vaadin.browserless.SpringBrowserlessApplicationContext;
import com.vaadin.flow.component.avatar.Avatar;
import com.vaadin.flow.router.RouteNotFoundError;

@SpringJUnitConfig({ SecurityTestConfig.class, TestViewSecurityConfig.class })
class SpringUnitSecurityTest {

    @Autowired
    private ApplicationContext applicationContext;

    @Autowired
    private UserDetailsService userDetailsService;

    private SecuredBrowserlessApplicationContext<Authentication> app;

    @BeforeEach
    void setUp() {
        app = SpringBrowserlessApplicationContext.createSecured(
                applicationContext, AdminRoleView.class);
    }

    @AfterEach
    void tearDown() {
        app.close();
    }

    @Test
    void superuser_adminView_viewShown() {
        var window = openWindowAs("admin");
        window.navigate(AdminRoleView.class);

        Assertions.assertTrue(
                window.find(Avatar.class).single().isVisible(),
                "Avatar should be visible for logged users");
    }

    @Test
    void user_adminView_accessDenied() {
        var window = openWindowAs("user");
        RouteNotFoundError errorView = window.navigate("admin-role",
                RouteNotFoundError.class);
        Assertions.assertTrue(
                errorView.getElement().getChild(0).getOuterHTML()
                        .contains("Reason: Access is denied"),
                "Admin view should be accessible only by users with ADMIN role");
    }

    private BrowserlessUIContext openWindowAs(String username) {
        UserDetails user = userDetailsService.loadUserByUsername(username);
        return app.newUser(UsernamePasswordAuthenticationToken.authenticated(
                user, user.getPassword(), user.getAuthorities())).newWindow();
    }
}

@TestConfiguration
class SecurityTestConfig {

    @Bean
    UserDetailsService mockUserDetailsService() {

        return new UserDetailsService() {
            @Override
            public UserDetails loadUserByUsername(String username)
                    throws UsernameNotFoundException {
                if ("user".equals(username)) {
                    return new User(username, UUID.randomUUID().toString(),
                            List.of(
                                new SimpleGrantedAuthority("ROLE_DEV"),
                                new SimpleGrantedAuthority("ROLE_USER")
                        ));
                }
                if ("admin".equals(username)) {
                    return new User(username, UUID.randomUUID().toString(),
                            List.of(
                                new SimpleGrantedAuthority("ROLE_SUPERUSER"),
                                new SimpleGrantedAuthority("ROLE_ADMIN")
                        ));
                }
                throw new UsernameNotFoundException(
                        "User " + username + " not exists");
            }
        };
    }
}
----

With [annotationname]`@SpringBootTest`, inject the application's own [classname]`UserDetailsService` in the same way.


[#authentication-applied-during-a-test]
=== Navigate after Changing Authentication

A user's credentials are in place before its window opens, so the window's first navigation already observes them.
When a test changes the authentication later -- for example, by running the application's own programmatic login in the window -- navigate again to apply access control to the new authentication:

[source,java]
----
var window = app.newUser().newWindow();
window.navigate("admin-role", LoginView.class);

// Run the application's own login action here.

// The window still shows the login view. Navigating again applies
// access control to the current authentication.
window.navigate(AdminRoleView.class);
----

The secured context keeps the authentication that a window of the user changes, and the user's other windows observe it as well.
See <<{articles}/flow/testing/browserless/environment-differences#authentication-applied-during-a-test,Authentication Timing>> for why reloading the current location does not replace this step.


[#spring-security-annotations]
=== Use Spring Security Test Annotations

A test that extends [classname]`SpringBrowserlessTest` simulates its user with Spring Security test annotations instead -- such as [annotationname]`@WithMockUser`, [annotationname]`@WithAnonymousUser`, or [annotationname]`@WithUserDetails`.
The annotations require the Spring Security test dependency:

[source,xml]
----
<dependency>
        <groupId>org.springframework.security</groupId>
        <artifactId>spring-security-test</artifactId>
        <scope>test</scope>
</dependency>
----

The authentication is in place before the base class creates the UI and navigates to the default route.
See the https://docs.spring.io/spring-security/reference/servlet/test/method.html#test-method-withmockuser[Spring Security documentation] for the annotations.

.Base-Class Tests with Mock Users
[source,java]
----
import org.junit.jupiter.api.Assertions;
import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.security.test.context.support.WithAnonymousUser;
import org.springframework.security.test.context.support.WithMockUser;
import com.vaadin.browserless.SpringBrowserlessTest;
import com.vaadin.flow.component.avatar.Avatar;
import com.vaadin.flow.component.html.Anchor;

@SpringBootTest
public class ViewSecurityTest extends SpringBrowserlessTest {

    @Test
    @WithAnonymousUser
    void anonymousUser_protectedView_redirectToLogin() {
        navigate("protected", LoginView.class);
    }

    @Test
    @WithAnonymousUser
    void anonymousUser_publicView_signInLinkPresent() {
        // public view is default page
        Assertions.assertInstanceOf(PublicView.class, getCurrentView());

        Anchor anchor = find(Anchor.class).withText("Sign in").single();
        Assertions.assertTrue(
                test(anchor).isUsable(),
                "Sign in link should be available for anonymous user");
    }

    @Test
    @WithMockUser(username = "admin", roles = "ADMIN")
    void adminUser_adminView_viewShown() {
        navigate(AdminRoleView.class);

        Assertions.assertTrue(
                find(Avatar.class).single().isVisible(),
                "Avatar should be visible for logged users");
    }
}
----

An annotation with `setupBefore = TestExecutionEvent.TEST_EXECUTION` establishes the authentication only after the initial navigation, so navigate again as described in <<#authentication-applied-during-a-test,Navigate after Changing Authentication>>.

[CAUTION]
In base-class tests, overriding beans with [annotationname]`@MockitoBean` or [annotationname]`@MockBean` makes Spring cache a separate application context for that test class. In a multi-class run, this can prevent the simulated user from being applied during navigation, causing protected views to redirect unexpectedly to the login view -- sometimes in *other* test classes. If security navigation tests fail only when the whole suite runs, suspect a bean override elsewhere. See <<{articles}/building-apps/testing/browserless/speed-up-tests#using-a-reduced-application-context,Using a Reduced Application Context>> for a context-friendly way to replace services.


[#quarkus]
== Quarkus Security

Start with <<{articles}/building-apps/testing/browserless/setup-quarkus#,the Quarkus test setup>>.

=== Set Up View Access Control

The Vaadin Quarkus extension doesn't register view access control automatically, so browserless tests register it themselves.
Vaadin applies access control through a [classname]`NavigationAccessControl` registered as a [classname]`BeforeEnterListener` for the UI.
Register it in a [classname]`QuarkusTestProfile` class that provides an observer for the Vaadin [classname]`ServiceInitEvent`:

.NavigationAccessControl for Quarkus Project Test
[source,java]
----
import jakarta.enterprise.event.Observes;
import com.vaadin.browserless.quarkus.mocks.MockQuarkusServletService;
import com.vaadin.flow.server.ServiceInitEvent;
import com.vaadin.flow.server.auth.NavigationAccessControl;
import io.quarkus.arc.profile.IfBuildProfile;
import io.quarkus.test.junit.QuarkusTestProfile;

public class ViewSecurityTestProfile implements QuarkusTestProfile {

    @Override
    public String getConfigProfile() {
        return "test-security"; // <1>
    }

    @IfBuildProfile("test-security") // <1>
    public static class NavigationAccessControlObserver {

        public void serviceInit(@Observes ServiceInitEvent event) { // <2>
            // @QuarkusTest starts the whole application, so we check
            // the VaadinService type to enable access control only for
            // browserless tests
            if (event.getSource() instanceof MockQuarkusServletService) { // <3>
                event.getSource().addUIInitListener(uiEvent -> {
                    // Customize the NavigationAccessControl as needed
                    NavigationAccessControl accessControl = new NavigationAccessControl();
                    accessControl.setLoginView(LoginView.class);

                    uiEvent.getUI().addBeforeEnterListener(accessControl);
                });
            }
        }
    }
}
----
<1> Sets the configuration profile to be used for the test. The observer class is annotated with [annotationname]`@IfBuildProfile`, so it's active only in tests that use this profile.
<2> Listens for Vaadin [classname]`ServiceInitEvent`. This is the same as implementing [classname]`VaadinServiceInitListener` and registering the class to be loaded by Java [classname]`ServiceLoader`.
<3> Checks that execution is started by the browserless test. This is required because [annotationname]`@QuarkusTest` causes the whole application to start when running the test.


[#quarkus-secured-context]
=== Simulate Users with a Secured Context

When Quarkus Security is active in the application, create the browserless application context with [methodname]`createSecured()`, and give each user the credentials to simulate when you create it:

* [methodname]`newUser()` creates an anonymous user.
* [methodname]`newUser("admin", "ADMIN")` creates an authenticated user with the given username and roles.
* [methodname]`newUser(identity)` installs any [classname]`SecurityIdentity`, such as one built with [classname]`QuarkusSecurityIdentity`:
+
[source,java]
----
SecurityIdentity identity = QuarkusSecurityIdentity.builder()
        .setPrincipal(new QuarkusPrincipal("john"))
        .addRoles(Set.of("USER"))
        .setAnonymous(false)
        .build();

var window = app.newUser(identity).newWindow();
----

As with Spring, the credentials are in place before the user's window opens and navigates to the default route, so logged-in users aren't redirected to the login view:

.Tests with Simulated Users
[source,java]
----
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.Assertions;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import com.vaadin.browserless.SecuredBrowserlessApplicationContext;
import com.vaadin.browserless.quarkus.QuarkusBrowserlessApplicationContext;
import com.vaadin.flow.component.avatar.Avatar;
import com.vaadin.flow.component.html.Anchor;
import io.quarkus.security.identity.SecurityIdentity;
import io.quarkus.test.junit.QuarkusTest;
import io.quarkus.test.junit.TestProfile;

@QuarkusTest
@TestProfile(ViewSecurityTestProfile.class) // <1>
class ViewSecurityTest {

    private SecuredBrowserlessApplicationContext<SecurityIdentity> app;

    @BeforeEach
    void setUp() {
        app = QuarkusBrowserlessApplicationContext
                .createSecured(PublicView.class);
    }

    @AfterEach
    void tearDown() {
        app.close();
    }

    @Test
    void anonymousUser_protectedView_redirectToLogin() {
        var window = app.newUser().newWindow(); // <2>

        window.navigate("protected", LoginView.class);
    }

    @Test
    void anonymousUser_publicView_signInLinkPresent() {
        var window = app.newUser().newWindow();

        // public view is default page
        Assertions.assertInstanceOf(PublicView.class, window.getCurrentView());

        Anchor anchor = window.find(Anchor.class).withText("Sign in").single();
        Assertions.assertTrue(
                window.test(anchor).isUsable(),
                "Sign in link should be available for anonymous user");
    }

    @Test
    void adminUser_adminView_viewShown() {
        var window = app.newUser("admin", "ADMIN").newWindow(); // <3>

        window.navigate(AdminRoleView.class);

        Assertions.assertTrue(
                window.find(Avatar.class).single().isVisible(),
                "Avatar should be visible for logged users");
    }
}
----
<1> Selects the test profile that registers view access control.
<2> Creates an anonymous user.
<3> Creates an authenticated user with the `ADMIN` role.

[#quarkus-test-security]
=== Use Quarkus Test Security

A test that extends [classname]`QuarkusBrowserlessTest` simulates its user with the Quarkus [annotationname]`@TestSecurity` annotation instead.
When Quarkus Security is on the classpath, the base class reads the authentication details from the Quarkus [classname]`SecurityIdentity`, before it creates the UI and navigates to the default route.
See the https://quarkus.io/guides/security-testing[Quarkus Security Testing documentation] for the annotation.

Add the Quarkus Security test dependency:

[source,xml]
----
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-test-security</artifactId>
    <scope>test</scope>
</dependency>
----

Annotate the test methods with [annotationname]`@TestSecurity`, providing the username and roles that should be granted:

.Base-Class Tests with Mock Users
[source,java]
----
import org.junit.jupiter.api.Assertions;
import org.junit.jupiter.api.Test;
import com.vaadin.browserless.quarkus.QuarkusBrowserlessTest;
import com.vaadin.flow.component.avatar.Avatar;
import io.quarkus.test.junit.QuarkusTest;
import io.quarkus.test.junit.TestProfile;
import io.quarkus.test.security.TestSecurity;

@QuarkusTest
@TestProfile(ViewSecurityTestProfile.class)
class ViewSecurityTest extends QuarkusBrowserlessTest {

    @Test // <1>
    void anonymousUser_protectedView_redirectToLogin() {
        navigate("protected", LoginView.class);
    }

    @Test
    @TestSecurity(user = "admin", roles = "ADMIN") // <2>
    void adminUser_adminView_viewShown() {
        navigate(AdminRoleView.class);

        Assertions.assertTrue(
                find(Avatar.class).single().isVisible(),
                "Avatar should be visible for logged users");
    }
}
----
<1> A test without [annotationname]`@TestSecurity` runs as an anonymous user. Don't use `@TestSecurity(authorizationEnabled = false)` for this: it disables Quarkus security checks, such as [annotationname]`@RolesAllowed` on services that the view calls.
<2> Simulates an authenticated user with the `ADMIN` role.

== Run the Security Tests

Run the security tests together with the rest of the suite using `mvn test`.
For concurrent users and security isolation, see <<{articles}/building-apps/testing/browserless/test-multiple-users#,Test Multiple Users and Windows>>.

= Browserless Testing

Browserless tests exercise Flow views and components in the test JVM, without a browser or a servlet container.
A test creates an application context, opens a window for a simulated user, and drives the UI through that window.
Choose the setup that matches your application's dependency injection framework before writing a test.

[#application-users-and-windows]
== Application, Users, and Windows

A browserless test models the application the way its users see it:

* The _application context_ plays the role of the deployed application. A test creates it and closes it when the test ends, or, in Spring Boot, a test configuration defines it once as a bean that the tests share.
* A _user_, created with [methodname]`newUser()`, has its own Vaadin session and, in a secured application, its own credentials.
* A _window_, created with [methodname]`newWindow()`, is one browser window of that user. It opens the root route, and the test navigates, finds components, and simulates user actions through it.

Most tests need one user with one window.
The same API covers <<test-multiple-users#,several users and windows>> when the behavior under test depends on them.

Quarkus has its own integration, even though it also uses CDI.
The Java EE/CDI guide uses the `jakarta.*` packages that current Vaadin versions require.

[#use-examples-with-your-framework]
== Use the Examples with Your Framework

The window methods that tests use to interact with the UI, such as [methodname]`navigate()`, [methodname]`findButton()`, and [methodname]`test()`, work the same in every setup.
Only the code that creates the application context differs.

Most examples in the other guides use the plain Java setup, with a `window` field that a [annotationname]`@BeforeEach` method creates, as in <<setup-without-spring#,the plain Java setup guide>>.
To use an example with another framework, keep the test methods, and create the application context as your framework's setup guide does:

* Spring Boot: annotate the class with [annotationname]`@SpringBootTest`, and autowire the [classname]`BrowserlessApplicationContext` bean that the setup guide defines, instead of creating the context in the [annotationname]`@BeforeEach` method. Close the window's user in the [annotationname]`@AfterEach` method instead of closing the context. Spring beans and Spring test configuration apply.
* Quarkus: annotate the class with [annotationname]`@QuarkusTest`, and create the context with `QuarkusBrowserlessApplicationContext.create()`. Quarkus test profiles apply.
* Java EE/CDI: extend [classname]`AbstractCdiViewTest`, add the tested view and its beans to its Weld archive, and register the view's route in its setup method. Call the window methods on the test itself, for example `navigate(...)` instead of `window.navigate(...)`.

[#base-classes]
== Base Classes

Tests can also extend a base class -- [classname]`BrowserlessTest`, [classname]`SpringBrowserlessTest`, or [classname]`QuarkusBrowserlessTest` -- that creates the Vaadin environment with one user and one window before each test method, and closes it afterwards.
The test then calls the window methods on itself, so `window.navigate(...)` becomes `navigate(...)`; for the locator methods, such as [methodname]`findButton()`, the test class also implements [interfacename]`Locators`.
Each setup guide also shows the base-class form of its test.

Use an application context for new tests.
A base class supports only one user and one window, and the test configures it with annotations, such as [annotationname]`@ViewPackages`, instead of in the code that creates the context.
Spring Security and Quarkus test annotations, such as [annotationname]`@WithMockUser` and [annotationname]`@TestSecurity`, apply to a base-class test; a secured application context takes the credentials of each user from [methodname]`newUser()` instead.

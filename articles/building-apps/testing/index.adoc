= Testing

These guides show you how to test the server-side behavior of Flow views using browserless tests.
Start by <<browserless#choose-your-framework,choosing the setup for your application framework>>, then choose a guide for the behavior you need to verify.

Browserless tests run against Java components without a browser.
Use browser-based tests when you need to verify rendering, client-side behavior, or real browser interactions.
See <<{articles}/flow/testing#comparison,the testing reference>> for a comparison of the approaches.


== Choosing What to Test

Each layer of your application is tested in its own way. The following table shows where to find guidance for each:

|Application services and their rules, including access control

|Queries, migrations, and the database schema
|Integration tests against the same database as in production
|<<../forms-data/persistence/replace-h2#add-testcontainers,Add Testcontainers>>, and https://docs.spring.io/spring-boot/reference/testing/testcontainers.html[Testcontainers] in the Spring Boot documentation

|Flow views
|Browserless tests
|The guides listed below

|Rendering, client-side behavior, and the whole application in a browser
|End-to-end tests
|<<{articles}/flow/testing/end-to-end#,End-to-End Testing>> and <<{articles}/flow/testing/playwright#,Testing with Playwright>>
|===

Service and browserless tests are fast and don't need a browser, so they can cover most of your application, including its use cases from start to finish. Keep end-to-end tests for what only a browser can show, as described in <<#browser-tests,Keep a Thin Layer of Browser Tests>>.

Browserless tests can't test <<../react#,React views>>, because React views run in the browser. Test the browser-callable services of a React view like any other application service, and the view itself with end-to-end tests, or with the JavaScript tools described in <<{articles}/hilla/guides/testing#,Testing>> in the Hilla reference.

To run the tests on every change, see <<../production/ci#,Build on CI>>.


[#browser-tests]
== Keep a Thin Layer of Browser Tests

Browserless tests prove behavior, not rendering.
They can't show that:

* the theme and the CSS look right,
* the client-side JavaScript of a component works,
* the layout works in real browsers and at different screen sizes, or
* add-ons and custom components render.

Keep a few end-to-end tests in a real browser for these, also as a safety net when you upgrade Vaadin or an add-on.
Typical smoke tests check that:

* the most important views open,
* custom components and add-ons render,
* the browser console shows no JavaScript errors,
* the login flow works, and
* each kind of gesture, such as drag and drop, reaches the server-side code that handles it; see <<browserless/test-custom-components#gestures,Design Gestures for Testing>>.

Don't repeat the use cases in the browser tests: the rules behind them belong in the faster browserless tests.
A component with client-side code of its own also needs browser tests for that code, in the component's own module.

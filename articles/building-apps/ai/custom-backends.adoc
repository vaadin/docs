= [since:com.vaadin:vaadin@V25.4]#Custom Backends for AI-Powered Grids and Charts#

include::{articles}/_vaadin-version.adoc[]

:preview-feature: AI integration features
:feature-flag: com.vaadin.experimental.aiComponents
include::{articles}/_preview-banner.adoc[opts=optional]

The <<{articles}/flow/ai-support/ai-powered-grid#,AI-powered Grid>> and <<{articles}/flow/ai-support/ai-powered-chart#,Chart>> let users explore data in natural language. The LLM reads a schema description, writes SQL, and a <<{articles}/flow/ai-support/controllers#database-provider,[classname]`DatabaseProvider`>> runs the query. When your data lives behind a REST API, in a service, or in files, no database runs that SQL for you.

This guide shows two ways to run it. The first is https://calcite.apache.org[Apache Calcite], a Java library that parses SQL and executes it over tables you define in Java. The LLM keeps writing standard SQL, and your provider answers from any data you can load into Java objects. You don't need prior experience with Calcite. The second is to copy the data into a database, which then runs the SQL.


== Prerequisites

* An application with an AI-powered Grid or Chart, set up as described on <<{articles}/flow/ai-support/ai-powered-grid#,AI-Powered Grid>> or <<{articles}/flow/ai-support/ai-powered-chart#,AI-Powered Chart>>. The two controllers belong to the commercial `vaadin-ai-extensions-flow` module and require a commercial Vaadin subscription. [classname]`DatabaseProvider` itself belongs to the open-source `vaadin-ai-core-flow` module.
* The `com.vaadin.experimental.aiComponents` <<{articles}/flow/configuration/feature-flags#,feature flag>> enabled: add `com.vaadin.experimental.aiComponents=true` to [filename]`src/main/resources/vaadin-featureflags.properties`.
* A Java client for your backend that returns the data as Java objects, for example a class that wraps Spring's [classname]`RestClient`. This guide calls it [classname]`CatalogClient`.


== Choose an Approach

A data source that has a JDBC driver needs neither approach of this guide. Query it with a JDBC provider like the one on the <<{articles}/flow/ai-support/controllers#database-provider,Controllers>> page.

Use Calcite when:

* your data has no SQL interface, such as a REST API, a gRPC service, or a set of files, or
* you want the LLM to join, group, and total data from several such sources in one query.

Every query loads the tables it uses into memory. Calcite therefore suits data that fits in the server's memory with room to spare for every user who queries it at the same time. Calcite reads the backend when a query runs, so the grid shows the backend's current data, as fresh as the short cache described later allows. One provider can combine several backends, and Calcite can pass simple conditions to the backend, as <<#pass-conditions,Pass Conditions to the Backend>> shows.

For data that is too large to load, Calcite can hand sorting, paging, and grouping to the backend as well. This takes an adapter, either one that Calcite ships or one that you write. See <<#backend-adapters,Run More of the Query in the Backend>>.

<<#database-copy,Copy the data into a database>> when the data doesn't fit in memory. A copy is also the simpler choice for data that seldom changes. The database then filters, sorts, pages, and groups the rows, and the grid shows the data as of the last refresh of the copy.


== Add the Dependency

Add `calcite-core` to your project:

[source,xml,subs="+attributes"]
----
<dependency>
    <groupId>org.apache.calcite</groupId>
    <artifactId>calcite-core</artifactId>
    <version>{calcite-version}</version>
</dependency>
----

Calcite shares libraries with Vaadin, such as SLF4J and the Jackson annotations, and declares older versions of them. The Vaadin BOM aligns the SLF4J version in every project. In a Spring Boot project, Spring Boot's dependency management aligns the Jackson annotations as well, so the dependency needs no exclusions. In a project without Spring Boot, exclude `com.fasterxml.jackson.core:jackson-annotations` from Calcite, so that its older version doesn't replace the one Vaadin's Jackson uses. Calcite brings many other transitive dependencies. The command `mvn dependency:tree` lists them.


== Describe the Data as Tables

Calcite runs SQL over tables that you define in Java. A table tells Calcite two things:

* its row type: the column names and their SQL types, and
* how to read its rows: a method that returns every row as an `Object[]`.

This guide exposes the products and orders of a [classname]`CatalogClient`, which stands for the client of your REST API or service. The client returns records like these:

[source,java]
----
public interface CatalogClient {
    List<Product> products();

    List<Order> orders();
}

public record Product(Integer id, String name, String category,
        BigDecimal price, Boolean discontinued) {
}

public record Order(Integer id, Integer productId, Integer quantity,
        LocalDate orderedOn) {
}
----

The following reusable classes turn such a list of objects into a Calcite table. They and the provider belong to one package. A [classname]`Column` describes one column with a name, a Java type, and a function that reads the value from an object:

[source,java]
----
import java.util.function.Function;

public record Column<T>(String name, Class<?> type,
        Function<T, Object> value) {
}
----

[classname]`BackendTable` holds the columns and a function that loads the objects from the backend:

[source,java]
----
import java.math.BigDecimal;
import java.time.Duration;
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.ZoneOffset;
import java.util.ArrayList;
import java.util.List;
import java.util.function.Supplier;

import org.apache.calcite.DataContext;
import org.apache.calcite.linq4j.Enumerable;
import org.apache.calcite.linq4j.Linq4j;
import org.apache.calcite.rel.type.RelDataType;
import org.apache.calcite.rel.type.RelDataTypeFactory;
import org.apache.calcite.schema.ScannableTable;
import org.apache.calcite.schema.impl.AbstractTable;
import org.apache.calcite.sql.type.SqlTypeName;

import com.vaadin.flow.component.ai.provider.ToolException;

public class BackendTable<T> extends AbstractTable implements ScannableTable {

    private static final Duration CACHE_FOR = Duration.ofSeconds(10);
    private static final int MAX_ROWS = 10_000;

    private final List<Column<T>> columns;
    private final Supplier<List<T>> loader;
    private List<T> cached;
    private long cachedUntil;

    public BackendTable(List<Column<T>> columns, Supplier<List<T>> loader) {
        this.columns = columns;
        this.loader = loader;
    }

    @Override
    public RelDataType getRowType(RelDataTypeFactory typeFactory) {
        return rowType(typeFactory, columns);
    }

    @Override
    public Enumerable<Object[]> scan(DataContext root) {
        return rows(columns, items());
    }

    // The grid reads a table several times per render: for a sample
    // row, for the row count, and for each page
    private synchronized List<T> items() {
        var now = System.nanoTime();
        if (cached == null || now - cachedUntil > 0) {
            cached = loader.get();
            cachedUntil = now + CACHE_FOR.toNanos();
        }
        return cached;
    }

    static <T> RelDataType rowType(RelDataTypeFactory typeFactory,
            List<Column<T>> columns) {
        var builder = typeFactory.builder();
        for (var column : columns) {
            var type = sqlType(typeFactory, column.type());
            builder.add(column.name(),
                    typeFactory.createTypeWithNullability(type, true));
        }
        return builder.build();
    }

    static <T> Enumerable<Object[]> rows(List<Column<T>> columns,
            List<T> items) {
        if (items.size() > MAX_ROWS) {
            // The message is passed to the LLM
            throw new ToolException("A table of the query has more than "
                    + MAX_ROWS + " rows, which is too many to query.");
        }
        var result = new ArrayList<Object[]>();
        for (var item : items) {
            var values = new Object[columns.size()];
            for (int i = 0; i < values.length; i++) {
                values[i] = toCalcite(columns.get(i).value().apply(item));
            }
            result.add(values);
        }
        return Linq4j.asEnumerable(result);
    }

    static RelDataType sqlType(RelDataTypeFactory typeFactory,
            Class<?> type) {
        if (type == Integer.class) {
            return typeFactory.createSqlType(SqlTypeName.INTEGER);
        } else if (type == Long.class) {
            return typeFactory.createSqlType(SqlTypeName.BIGINT);
        } else if (type == Double.class) {
            return typeFactory.createSqlType(SqlTypeName.DOUBLE);
        } else if (type == BigDecimal.class) {
            return typeFactory.createSqlType(SqlTypeName.DECIMAL, 19, 4);
        } else if (type == Boolean.class) {
            return typeFactory.createSqlType(SqlTypeName.BOOLEAN);
        } else if (type == LocalDate.class) {
            return typeFactory.createSqlType(SqlTypeName.DATE);
        } else if (type == LocalDateTime.class) {
            return typeFactory.createSqlType(SqlTypeName.TIMESTAMP);
        }
        return typeFactory.createSqlType(SqlTypeName.VARCHAR);
    }

    // Calcite represents dates as days and timestamps as milliseconds
    // since the epoch
    static Object toCalcite(Object value) {
        if (value instanceof LocalDate date) {
            return (int) date.toEpochDay();
        } else if (value instanceof LocalDateTime timestamp) {
            return timestamp.toInstant(ZoneOffset.UTC).toEpochMilli();
        }
        return value;
    }
}
----

Some details of this class matter:

* Calcite expects every value in a fixed Java representation. `Integer`, `Long`, `Double`, `BigDecimal`, `Boolean`, and `String` values pass as they are. A date is the number of days since January 1, 1970, and a timestamp the number of milliseconds since then, which is what [methodname]`toCalcite()` produces for [classname]`LocalDate` and [classname]`LocalDateTime` values. Any other Java type is declared as `VARCHAR`, so the column's function has to return a `String` for it, for example `item -> item.status().name()`.
* To map another type, add it to [methodname]`sqlType()` and [methodname]`toCalcite()`. For an [classname]`Instant`, for example, return `TIMESTAMP` and [methodname]`toEpochMilli()`. The grid then shows the time in Coordinated Universal Time (UTC).
* Every column is nullable, so a `null` in a Java object becomes SQL `NULL`.
* A grid render reads a table several times: for a sample row that decides the columns, for the row count, and for each page. The table keeps the loaded objects for a short time, so a render costs one backend call. Set the duration to how fresh the data has to be.
* A query on a table with more than `MAX_ROWS` rows fails with a [classname]`ToolException`, whose message tells the LLM that the table is too large. Calcite then doesn't sort, join, or group that many rows in memory. The client has loaded the rows by then, so have the client stop reading when it passes the limit as well.


== Implement the Provider

The provider opens a Calcite connection, registers the tables under a schema name, and runs each query through plain JDBC:

[source,java]
----
import java.math.BigDecimal;
import java.sql.DriverManager;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.time.LocalDate;
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Properties;
import java.util.stream.Collectors;

import org.apache.calcite.jdbc.CalciteConnection;
import org.apache.calcite.runtime.CalciteContextException;
import org.apache.calcite.schema.impl.AbstractSchema;
import org.apache.calcite.sql.parser.SqlParseException;

import com.vaadin.flow.component.ai.common.QueryPage;
import com.vaadin.flow.component.ai.provider.DatabaseProvider;
import com.vaadin.flow.component.ai.provider.ToolException;
import com.vaadin.flow.data.provider.SortDirection;

public class CatalogDatabaseProvider implements DatabaseProvider {

    private static final String GENERIC_ERROR = "The query could not be executed.";

    private final CatalogClient client;
    private transient CalciteConnection connection;

    public CatalogDatabaseProvider(CatalogClient client) {
        this.client = client;
    }

    @Override
    public String getSchema() {
        return """
                Tables:
                products(id INT, name VARCHAR, category VARCHAR, price DECIMAL, discontinued BOOLEAN)
                orders(id INT, product_id INT, quantity INT, ordered_on DATE)
                orders.product_id refers to products.id.
                Dialect: Apache Calcite, standard SQL. JOIN, GROUP BY, sub-queries, LIMIT and OFFSET are supported.
                Compare DATE columns with DATE literals, for example ordered_on >= DATE '2025-01-01'.
                Put a column alias that is a SQL keyword, such as value or year, in double quotes: SUM(quantity) AS "value".
                """;
    }

    @Override
    public synchronized List<Map<String, Object>> executeQuery(String sql) {
        try (var statement = connection().createStatement();
                var resultSet = statement
                        .executeQuery(withoutTrailingSemicolon(sql))) {
            return rows(resultSet);
        } catch (SQLException | RuntimeException e) {
            // Calcite throws a failure that occurs while the query runs,
            // such as a CAST of text to a number, as an unchecked exception
            throw new ToolException(messageForLlm(e), e);
        }
    }

    @Override
    public List<Map<String, Object>> executeQuery(String sql,
            QueryPage page) {
        var paged = withoutTrailingSemicolon(sql);
        if (!page.sortOrders().isEmpty()) {
            // The grid's sort replaces an ORDER BY the LLM wrote
            paged = "SELECT * FROM (" + paged + "\n) AS page ORDER BY "
                    + page.sortOrders().stream()
                            .map(order -> "\""
                                    + order.getSorted().replace("\"", "\"\"")
                                    + "\" "
                                    + (order.getDirection() == SortDirection.DESCENDING
                                            ? "DESC"
                                            : "ASC"))
                            .collect(Collectors.joining(", "));
        }
        // The line breaks keep a comment at the end of the LLM's SQL from
        // swallowing what follows it
        return executeQuery(
                paged + "\nLIMIT " + page.limit() + " OFFSET " + page.offset());
    }

    private CalciteConnection connection() throws SQLException {
        if (connection == null) {
            var properties = new Properties();
            // Unquoted names are case-insensitive; quoting uses double
            // quotes as in standard SQL
            properties.setProperty("lex", "MYSQL_ANSI");
            connection = DriverManager
                    .getConnection("jdbc:calcite:", properties)
                    .unwrap(CalciteConnection.class);
            var schema = connection.getRootSchema().add("catalog",
                    new AbstractSchema());
            schema.add("products", new BackendTable<>(List.of(
                    new Column<Product>("id", Integer.class, Product::id),
                    new Column<Product>("name", String.class, Product::name),
                    new Column<Product>("category", String.class,
                            Product::category),
                    new Column<Product>("price", BigDecimal.class,
                            Product::price),
                    new Column<Product>("discontinued", Boolean.class,
                            Product::discontinued)),
                    client::products));
            schema.add("orders", new BackendTable<>(List.of(
                    new Column<Order>("id", Integer.class, Order::id),
                    new Column<Order>("product_id", Integer.class,
                            Order::productId),
                    new Column<Order>("quantity", Integer.class,
                            Order::quantity),
                    new Column<Order>("ordered_on", LocalDate.class,
                            Order::orderedOn)),
                    client::orders));
            connection.setSchema("catalog");
        }
        return connection;
    }

    private static List<Map<String, Object>> rows(ResultSet resultSet)
            throws SQLException {
        var metaData = resultSet.getMetaData();
        var rows = new ArrayList<Map<String, Object>>();
        while (resultSet.next()) {
            var row = new LinkedHashMap<String, Object>();
            for (int i = 1; i <= metaData.getColumnCount(); i++) {
                var value = resultSet.getObject(i);
                if (value instanceof java.sql.Date date) {
                    value = date.toLocalDate();
                } else if (value instanceof java.sql.Timestamp timestamp) {
                    value = timestamp.toLocalDateTime();
                }
                row.put(metaData.getColumnLabel(i), value);
            }
            rows.add(row);
        }
        return rows;
    }

    // Calcite rejects a statement that ends with a semicolon
    private static String withoutTrailingSemicolon(String sql) {
        var trimmed = sql.strip();
        return trimmed.endsWith(";")
                ? trimmed.substring(0, trimmed.length() - 1)
                : trimmed;
    }

    // Calcite's parse and validation errors describe the problem in the
    // SQL the LLM wrote, so they are safe to relay. A table writes the
    // message of its ToolException for the LLM.
    private static String messageForLlm(Exception exception) {
        for (Throwable cause = exception; cause != null; cause = cause
                .getCause()) {
            if (cause instanceof ToolException) {
                return cause.getMessage();
            }
            if (cause instanceof CalciteContextException
                    || cause instanceof SqlParseException) {
                var message = cause.getMessage();
                var expecting = message.indexOf("\nWas expecting");
                return expecting > 0 ? message.substring(0, expecting)
                        : message;
            }
        }
        return GENERIC_ERROR;
    }
}
----

How the parts work together:

* The `lex` setting makes unquoted names case-insensitive, so `SELECT Name FROM Products` finds the `name` column of `products`, and it makes double quotes the way to quote a name. The LLM and the grid both quote names that way.
* The connection is created on first use and is `transient`. The grid keeps a reference to the provider, so the provider is serialized with the session, and the client with it. Keep the client serializable, or mark it `transient` and look it up again when the connection is created, for example from the Spring application context.
* [methodname]`executeQuery()` is `synchronized`. It creates the connection on first use, and Calcite doesn't document its connections as safe for concurrent use. The grid can load a page while the LLM validates its next query, so both can run at the same time.
* Calcite returns dates as [classname]`java.sql.Date` and timestamps as [classname]`java.sql.Timestamp`. The provider converts them to [classname]`LocalDate` and [classname]`LocalDateTime`, which the grid renders with its date renderers.
* Calcite's parse and validation errors name the problem in the SQL the LLM wrote, such as an unknown column. The provider relays them in a [classname]`ToolException`, so the LLM can correct its query. The [classname]`ToolException` of a table with too many rows reaches the LLM with its own message. Every other failure, including the unchecked exceptions Calcite throws while a query runs, becomes a [classname]`ToolException` with a generic message.
* Calcite rejects a statement that ends with a semicolon, and LLMs often write one. The provider removes a trailing semicolon before it runs or wraps a query, so the LLM doesn't spend a turn on correcting it. It also starts what it adds after the LLM's SQL on a new line, so that a `--` comment at the end of the SQL doesn't swallow it.
* The grid loads rows one page at a time through [methodname]`executeQuery(String sql, QueryPage page)` and [methodname]`count(String sql)`. Their default implementations wrap the query in sub-queries, and Calcite drops an `ORDER BY` from a sub-query that has no `LIMIT` of its own. With the defaults, the grid loses a sort the user applies, and also an `ORDER BY` the LLM wrote, for example to list the most expensive products first. The override in the listing handles both cases. When the grid has no sort of its own, it appends `LIMIT` and `OFFSET` to the LLM's query. Otherwise it wraps the query, so that the grid's sort replaces the LLM's. The grid instructs the LLM not to write `LIMIT` or `OFFSET`. When a query has one anyway, the validation of the query fails, and the parse error tells the LLM why. The default [methodname]`count()` works as it is, and handles a trailing semicolon or comment at the end of the query by itself.


== Describe the Schema for the LLM

The text that [methodname]`getSchema()` returns is all the LLM knows about your data. The general advice on the <<{articles}/flow/ai-support/controllers#database-provider,Controllers>> page applies. Some points are specific to Calcite:

* Name the dialect. Calcite accepts standard SQL, including `JOIN`, `GROUP BY`, sub-queries, `LIMIT`, and `OFFSET`.
* Tell the LLM to write dates as `DATE` literals, for example `ordered_on >= DATE '2025-01-01'`, and timestamps as `TIMESTAMP` literals, for example `TIMESTAMP '2025-01-01 00:00:00'`.
* Avoid column names that are SQL keywords, such as `year`, `month`, `value`, or `order`. Calcite accepts them only in double quotes, and the LLM writes them unquoted unless told otherwise. Rename the column in the table definition, or say in the schema text that the name has to be quoted.
* This also applies to the column aliases the LLM chooses: `SUM(quantity) AS value` fails to parse, and `value` is a common alias in a chart query. Say in the schema text that an alias that is a keyword has to be in double quotes.
* With the `lex` setting shown earlier, table and column names are case-insensitive, so the LLM may write them as they appear in the description.


== Use the Provider

Create the provider in the view and pass it to a [classname]`GridAIController` or a [classname]`ChartAIController` like any other [classname]`DatabaseProvider`:

[source,java]
----
var provider = new CatalogDatabaseProvider(catalogClient);
var controller = new GridAIController(grid, provider);
----

Attach the controller to the orchestrator as described on <<{articles}/flow/ai-support/ai-powered-grid#,AI-Powered Grid>> and <<{articles}/flow/ai-support/ai-powered-chart#,AI-Powered Chart>>.

A provider created in the view belongs to one user: its connection, its cached rows, and the credentials its client uses are that user's. Share one provider between users, for example as a Spring bean, only when every user may see the same data. The cache then serves rows loaded for one user to the others, and all users' queries run one at a time.

The provider needs no LLM to test. A unit test can call [methodname]`executeQuery()` with hand-written SQL against a fake client and check the rows. This catches mistakes in the schema text, the type mapping, and the quoting before a model is involved.


== What to Expect at Runtime

Each query reads every table it uses in full, and Calcite filters, joins, sorts, and groups in memory. A sorted or paged grid query reads the whole table as well. The time and memory a query takes therefore grow with the size of the tables it reads, not with the size of its result. The row limit of [classname]`BackendTable` fails the queries on a table that has outgrown this approach. For large tables, <<#pass-conditions,pass conditions to the backend>>, <<#backend-adapters,run more of the query in the backend>>, or <<#database-copy,copy the data into a database>>.

The chart calls [methodname]`executeQuery(String sql)` for each of its series queries and receives the full result. It does so when the LLM proposes the queries, and again every time the chart renders, including after a state restore. A series query that groups its rows returns a small result, and the table cache serves the repeated calls.

Calcite can't change data through these tables. A `DELETE` or `UPDATE` fails before anything runs, so the provider is read-only by construction. The advice on the Controllers page about keeping secrets out of the schema text and error messages still applies.


[[pass-conditions]]
== Pass Conditions to the Backend

When your backend can filter, such as a REST endpoint with query parameters, let Calcite hand it the conditions of the `WHERE` clause. Implement [interfacename]`FilterableTable` instead of [interfacename]`ScannableTable`. Its [methodname]`scan()` receives the conditions as a list: you take the ones the backend understands and remove them from the list, and Calcite applies the rest itself. The following table passes `column = value` conditions to the loader as a map. It reuses [classname]`Column` and the helpers of [classname]`BackendTable`:

[source,java]
----
import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.function.Function;

import org.apache.calcite.DataContext;
import org.apache.calcite.linq4j.Enumerable;
import org.apache.calcite.plan.RelOptUtil;
import org.apache.calcite.rel.type.RelDataType;
import org.apache.calcite.rel.type.RelDataTypeFactory;
import org.apache.calcite.rex.RexCall;
import org.apache.calcite.rex.RexInputRef;
import org.apache.calcite.rex.RexLiteral;
import org.apache.calcite.rex.RexNode;
import org.apache.calcite.schema.FilterableTable;
import org.apache.calcite.schema.impl.AbstractTable;
import org.apache.calcite.sql.SqlKind;
import org.apache.calcite.util.DateString;

public class FilteringBackendTable<T> extends AbstractTable
        implements FilterableTable {

    private final List<Column<T>> columns;
    private final Function<Map<String, String>, List<T>> loader;

    public FilteringBackendTable(List<Column<T>> columns,
            Function<Map<String, String>, List<T>> loader) {
        this.columns = columns;
        this.loader = loader;
    }

    @Override
    public RelDataType getRowType(RelDataTypeFactory typeFactory) {
        return BackendTable.rowType(typeFactory, columns);
    }

    @Override
    public Enumerable<Object[]> scan(DataContext root,
            List<RexNode> filters) {
        var conditions = new LinkedHashMap<String, String>();
        var remaining = new ArrayList<RexNode>();
        for (var filter : filters) {
            var handled = true;
            for (var condition : RelOptUtil.conjunctions(filter)) {
                var equality = equality(condition);
                if (equality != null) {
                    conditions.put(equality.getKey(), equality.getValue());
                } else {
                    handled = false;
                }
            }
            if (!handled) {
                remaining.add(filter);
            }
        }
        // Calcite applies the filters left in the list itself
        filters.clear();
        filters.addAll(remaining);
        return BackendTable.rows(columns, loader.apply(conditions));
    }

    // Recognizes "column = literal" and "literal = column"
    private Map.Entry<String, String> equality(RexNode condition) {
        if (condition instanceof RexCall call
                && call.getKind() == SqlKind.EQUALS) {
            var left = call.getOperands().get(0);
            var right = call.getOperands().get(1);
            if (left instanceof RexInputRef column
                    && right instanceof RexLiteral literal) {
                return entry(column, literal);
            } else if (right instanceof RexInputRef column
                    && left instanceof RexLiteral literal) {
                return entry(column, literal);
            }
        }
        return null;
    }

    private Map.Entry<String, String> entry(RexInputRef column,
            RexLiteral literal) {
        var text = switch (literal.getTypeName()) {
        case CHAR, VARCHAR -> literal.getValueAs(String.class);
        case DECIMAL -> literal.getValueAs(BigDecimal.class)
                .stripTrailingZeros().toPlainString();
        case DATE -> String.valueOf(literal.getValueAs(DateString.class));
        default -> null; // other types are not passed to the backend
        };
        return text == null ? null
                : Map.entry(columns.get(column.getIndex()).name(), text);
    }
}
----

Register the table with a loader that takes the map, for example a method that turns it into query parameters of the endpoint:

[source,java]
----
schema.add("products", new FilteringBackendTable<>(productColumns,
        client::products)); // List<Product> products(Map<String, String> filters)
----

What to keep in mind:

* A condition stays in the list unless the table takes every part of it. For `WHERE category = 'Books' AND price > 10`, the table sends the category to the backend and leaves the whole condition to Calcite, which checks both parts again. Leaving a condition to Calcite is always safe. Removing one that the backend didn't apply returns wrong results.
* Calcite rewrites some conditions before they reach the table: an `IN` list arrives as a search over a set of values, and `discontinued = TRUE` arrives as the column on its own. [methodname]`equality()` recognizes neither, so both stay with Calcite.
* `ORDER BY`, `LIMIT`, and `OFFSET` don't reach the table. The backend returns every matching row, and Calcite sorts and cuts the page.
* This table has no cache, so a grid render calls the backend once for the sample row, once for the count, and once per page. If you add a cache, key it by the conditions, since each set of conditions loads different rows.


[[backend-adapters]]
== Run More of the Query in the Backend

The tables of this guide leave sorting, paging, and grouping to Calcite, which does them in memory. When the data is too large for that and a database copy isn't an option, Calcite can hand these parts of a query to the backend too. Do so in one of the following ways:

* Use an adapter that Calcite ships. Calcite has https://calcite.apache.org/docs/adapter.html[adapters] for several data stores, such as MongoDB, Elasticsearch, and Cassandra. An adapter replaces the tables you define: you register its schema on the connection. It translates the conditions, the sort, and the limit of a query into the query language of the data store, and some adapters translate the grouping as well. An adapter translates only a part of SQL, and a query with a part it can't translate can fail or return wrong rows. Test an adapter with the kinds of query the LLM writes before you rely on it, such as date conditions, `<>`, and `LIKE`.
* Write an adapter. For a backend without one, such as a REST API, implement [interfacename]`TranslatableTable` instead of [interfacename]`ScannableTable`. The table then takes part in planning the query. Planner rules that you write move a filter, a sort, a limit, or a grouping into the scan of the table, and the scan sends them to the backend. This is how Calcite's own adapters work, and the https://calcite.apache.org/docs/tutorial.html[Calcite tutorial] introduces the technique. It takes considerably more code than the tables in this guide, and knowledge of Calcite's planner.

With either kind of adapter, keep the provider of this guide, including its paging override. The override puts the sort, the limit, and the offset on the top level of one statement, which an adapter can hand to the backend as a whole. With the default paging, Calcite drops the sort, so the backend receives the limit without it and returns the wrong rows.

The grid also counts the rows of every query. The default [methodname]`count()` wraps the query in `SELECT COUNT(*)`, which the adapter has to translate as well. Otherwise, Calcite reads every matching row from the backend to count them.


[[database-copy]]
== Copy the Data into a Database

Instead of running the LLM's SQL over Java objects, the application can keep a copy of the data in a database and let the database run the SQL. The database filters, sorts, pages, and groups the rows, so this approach suits data that is too large for Calcite to load. The trade-off is that the grid and the chart show the data as of the last refresh of the copy.

Any database with a JDBC driver can hold the copy, such as a schema of its own in the database the application already uses, or an embedded database. Create the tables of the copy the way the application creates its other tables, for example with a migration tool.

The following Spring service fills the `products` table of the copy and refreshes it every ten minutes. It reads the products one page at a time, which requires a client method such as `List<Product> products(int page, int pageSize)`:

[source,java]
----
import java.sql.SQLException;
import java.sql.Types;
import java.util.List;
import java.util.concurrent.TimeUnit;

import javax.sql.DataSource;

import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Service;

@Service
public class CatalogCopy {

    private static final int PAGE_SIZE = 500;

    private final CatalogClient client;
    private final DataSource dataSource;

    public CatalogCopy(CatalogClient client, DataSource dataSource) {
        this.client = client;
        this.dataSource = dataSource;
    }

    @Scheduled(fixedDelay = 10, timeUnit = TimeUnit.MINUTES)
    public void refresh() throws SQLException {
        try (var connection = dataSource.getConnection()) {
            connection.setAutoCommit(false);
            try (var delete = connection.createStatement();
                    var insert = connection.prepareStatement("""
                            INSERT INTO products
                            (id, name, category, price, discontinued)
                            VALUES (?, ?, ?, ?, ?)""")) {
                delete.executeUpdate("DELETE FROM products");
                List<Product> page;
                int pageNumber = 0;
                do {
                    page = client.products(pageNumber++, PAGE_SIZE);
                    for (var product : page) {
                        insert.setInt(1, product.id());
                        insert.setString(2, product.name());
                        insert.setString(3, product.category());
                        insert.setBigDecimal(4, product.price());
                        // A Boolean that may be null
                        insert.setObject(5, product.discontinued(),
                                Types.BOOLEAN);
                        insert.addBatch();
                    }
                    insert.executeBatch();
                } while (page.size() == PAGE_SIZE);
                connection.commit();
            } catch (SQLException | RuntimeException e) {
                // Queries keep reading the previous copy
                connection.rollback();
                throw e;
            }
        }
    }
}
----

How the service works:

* It reads and inserts one page at a time, so the application never holds all the products in memory.
* It replaces the rows in one transaction, so a query never reads a half-filled table. Depending on the database, a query that runs during a refresh reads the previous copy or waits for the refresh to finish. A refresh that fails leaves the previous copy in place.
* Spring calls the [annotationname]`@Scheduled` method when the application starts and then again each time ten minutes have passed since the previous call ended. Scheduling requires [annotationname]`@EnableScheduling` on a configuration class. When a call fails, Spring logs the exception and calls the method again after the delay. In an application without Spring, schedule the refresh with a [classname]`ScheduledExecutorService`. Catch the exceptions of the refresh in the scheduled task, because the executor stops repeating a task that throws one.
* Choose the delay by how old the data may be and by how much load a full read puts on the backend.

Query the copy with a JDBC provider like the one on the <<{articles}/flow/ai-support/controllers#database-provider,Controllers>> page, and describe the tables of the copy in its [methodname]`getSchema()`. Give the provider a database account that can only read the copy, as that page advises.
